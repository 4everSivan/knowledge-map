# 术语知识卡片设计

> **created**: 2026-10-15 ｜ **last-change**: 2026-10-16 ｜ **status**: baseline

## 1. 简介

本设计适用于 km v0.1.0。用户于 2026-10-15 明确“0.1 版本的设计暂时定稿，按文档治理流程落地实现”，本组设计据此确认为该版本基线；实现与验收由 T01 记录，设计批准不等于运行能力验收。

术语知识卡片是 km 项目知识库中的结构化术语条目，用于解释项目出现的专业名称、缩写和独有名称。读者应能据此理解名称的含义、项目内用途和来源语境，而不是只得到一个脱离工程的通用定义。

本设计承接用户对知识卡片定位、输出目录和重复更新的澄清，以及总体设计中已经形成的术语模型。卡片由宿主 AI 遵循 workflow 文件生成、检查和更新，使用宿主已有工具；km 不提供或依赖执行脚本、独立执行引擎或脚本产物协议。本设计已确认为 v0.1 基线，协议由英文参考承载，交付与验收由 T01 记录。

用户已确认卡片保持精简，核实批次、哈希等更新记录集中到 `manifest.json`；释义与项目用途分别保留为 `definition` 和 `project_usage`，卡片可以绑定对应文章。文章关联使用 `articles` 数组，支持一张卡在多篇文章中复用。v0.1 固定卡片协议为 `1.0`，更新记录格式见[清单契约](../../../references/library-state.md)。

## 3. 规范

### 3.1 目标与职责

一张卡解释一个有明确项目语境的术语，回答以下问题：它是什么，在本项目中表示什么或承担什么职责，在哪里出现。相同文字在不同领域或模块中含义不同，必须区分语境，不能拼成一段混合释义。

Markdown 承载架构、模块设计、核心流程、操作步骤和业务规则等完整说明；JSON 卡片解释正文中的名称，并关联对应文档及原始证据。流程问答、操作清单和行为结论不替代术语条目，也不因需要机器读取就把整章文档复制进 JSON。

### 3.2 输入、输出与真实性

卡片内容以项目源码和原项目文档为工程依据。必要的权威参考只能补充专业术语的通用释义，不能取代项目来源来证明项目内用途。不得从文件或名称存在推断相关能力已接入主链路，不能把文档中的目标设计写成已经实现。

卡片的 `definition` 与 `project_usage` 分别记录依据。权威定义不自动证明项目行为，静态源码支持不等于生产运行验证；未经执行的测试也不能证明测试已经通过。存在冲突、缺少项目解释或缩写全称不明时，如实列为待确认项，不补造事实。

身份、来源和检查记录由宿主 AI 根据实际读取内容及可用工具维护，不假定存在自动身份分配器、哈希计算器或协议校验器。工具无法获得的值可以按字段约定缺省，并明确未核对范围；不得由模型编造哈希或已执行的检查结果。

生成区不作为下一轮的独立事实来源。受管文件发生外部修改时沿用整轮冲突保护，不把直接修改自动吸收为术语知识，不提供人工补充内容的收录或合并流程。

### 3.3 路径与协议边界

| 对象 | 路径与规则 |
|---|---|
| 正式知识文档 | 直接放在目标工程的 `docs/official/`，使用无编号的中文文件名和中文标题；导航入口 `README.md` 为文件名例外 |
| 术语卡片 | 直接放在 `docs/official/.cards/k_<uuid>.json`，不再嵌套 `cards/` 子目录 |
| 库级元数据 | `docs/official/.cards/manifest.json`，保存项目身份、受管文件、内容修订及按卡片 ID 关联的核实批次、可用哈希等更新记录 |
| 其它生成 JSON | 配置、尝试记录、本轮候选、检查及恢复记录均在 `.cards/` 下，运行批次使用 `.cards/runs/<run_id>/` |
| 卡片文章关联 | 以 `articles[].path` 保存相对于 `docs/official/` 的文章路径，`anchor` 按需定位章节；不能相对于 `.cards/` 解析 |
| 本地 `sources.path` | 相对于目标工程根目录解析，定位原源码或原项目文档；不使用作者机器的绝对路径 |

本文件属于治理设计，沿用 `docs/devel/design/02-术语知识卡片设计.md` 的既有编号规则；生产知识文档的无编号约定不迁移或重命名治理文件。卡片协议版本、技能版本和目标项目版本分别表达各自对象，不以其中一个代替其它版本。

## 4. 设计详情

### 4.1 收录与语义身份

<!-- @topic: KnowledgeCards -->

收录范围分为两类：

| `category` | 收录内容 | 边界 |
|---|---|---|
| `domain_term` | 项目实际涉及、需要解释的领域专业术语 | 通用释义必须落回项目的具体语境，不扩成与工程无关的百科条目 |
| `project_term` | 项目独有的名称、模块称谓、角色、状态或内部概念 | 名称须实际出现并承载可解释的概念，不因每个变量或函数都有名字就机械建卡 |

缩写和英文全称属于名称信息，不单独增加类别。`term` 保留项目中的规范拼写和大小写；`aliases` 只收录资料证实等价的别名。缩写对应的 `full_name` 有依据才填写，不能凭字母推测，也不能把含义相近的两个概念当作别名。

`term + context` 用于判断语义是否相同，不用作持久主键。一个术语在多个文件出现时，来源归于同一卡片；同一名称在不同语境代表不同概念时分别建卡。名称、来源路径或文字表述变化，不能单独决定是否新建身份。

### 4.2 字段协议

| 字段 | 要求 | 含义与约束 |
|---|---|---|
| `schema_version` | 必填 | 卡片结构协议版本，v0.1 固定为字符串 `1.0` |
| `id` | 必填 | `k_` 加 UUID，已有身份持续沿用；文件名为 `<id>.json`，不使用术语文字、行号或内容哈希代替身份；分配与冲突检查受实际工具能力限制 |
| `term` | 必填 | 项目实际使用的名称，保持规范拼写 |
| `aliases` | 可选 | 真实别名数组；没有经来源确认的别名时省略或使用空数组 |
| `full_name` | 可选 | 缩写在本语境中经来源确认的全称；不明时省略并保留待确认说明 |
| `category` | 必填 | 仅为 `domain_term` 或 `project_term` |
| `context` | 必填 | 明确领域、模块或业务语境，能区分同名异义 |
| `definition` | 必填 | 当前语境中的释义；通用含义与项目特殊含义不一致时说明边界 |
| `project_usage` | 必填 | 项目中的用途、职责或含义边界，不承载整段操作或流程 |
| `basis` | 必填 | 对象，分别设置 `definition` 与 `project_usage` 的依据类别 |
| `status` | 必填 | `current`、`stale` 或 `retired`，表示知识新鲜度，不代表生产验收 |
| `articles` | 可选 | 文章关联数组；每项 `path` 必填、`anchor` 可选。支持多篇文章，正式绑定的路径与锚点必须实际存在 |
| `sources` | 必填 | 支撑释义或项目用途的实际来源，包含来源位置和支持字段；单卡保留直接出处，批次和哈希由 manifest 记录 |
| `tags` | 可选 | 项目中适用的模块或检索标签，不代替语义身份和证据 |

用户已确认 `definition` 说明“它是什么”，`project_usage` 说明“本项目怎么用它”。两者不合并为 `description`；通用含义和项目用法的依据可以不同。

`basis.definition` 与 `basis.project_usage` 分别采用以下枚举；不能以单一字段把两类解释合并判定：

| 值 | 可以表达什么 | 不能据此表达什么 |
|---|---|---|
| `code_supported` | 已读取的静态源码支持该字段的解释 | 未经执行的运行行为、测试通过或生产验收 |
| `document_declared` | 原项目文档明确声明该含义、设计或用途 | 项目必然按文档实现 |
| `reference_supported` | 权威参考支持该字段实际描述的专业定义 | 参考资料未说明的项目实现或用途 |
| `inferred` | 已有资料上的推断，明确标记其不确定性 | 以确定语气补齐缺失事实或不明缩写 |

例如，通用定义可以是 `reference_supported`，而项目用途为 `code_supported`；两者必须各有对应来源。没有充分依据的项目用途保留在待确认项中，不为填齐字段编造完整卡片。

### 4.3 直接来源与集中更新记录

`sources` 中每项说明来源类别及其实际支持的字段。`supports` 明确该项支持 `definition`、`project_usage` 中的哪些字段；别名和缩写全称也必须能在所列来源中找到依据。

本地源码或文档使用项目根相对 `path`，并用实际符号、文档锚点或其它明确位置定位。行号可以辅助当前展示，但不是稳定身份。直接来源随卡片保留，便于单卡解释“依据在哪里”。

核实批次、核对时间、来源与产物哈希等更新信息集中保存在 manifest 的对应卡片记录中，不再要求单卡携带 `checked_in` 或 `source_hash`。哈希只有宿主工具实际取得时才记录，并说明计算对象；不能用当前文件内容伪装旧证据。

没有哈希能力时省略相应哈希，在核对记录中说明实际读取范围与未执行的比较。不能从文字、文件名或 Git 提交号推算哈希，也不能把缺省值解释为内容未变化。来源无法读取与哈希未取得分别说明。

使用外部权威参考时记录明确 URL 和实际查阅内容的依据，不将外部定义冒充本地源码证据。仅有一个出处链接不代替“该来源支持哪个解释”的说明。

来源批次记录项目身份、实际读取范围、有效扫描配置及 workflow 标识；输入哈希、Git 提交和工作区修改情况仅在宿主工具实际取得时记录，否则明确缺省或未核对。非 Git 工程仍以实际读取内容为准，不编造 Git 信息。这些来源记录不自动等同于不可变内容副本，也不承诺整个工作区取得了一致快照。

manifest 按稳定卡片 ID 关联更新记录。保留当前核实依据及确有追溯需要的历史信息，不因单卡字段存在或记录写入就声称取得完整快照。manifest 协议由 T03 扩展为 `2.0`，术语卡保持 `1.0`；保留当前记录引用的核实批次，具体字段见[状态参考](../../../references/library-state.md)和[工程制图设计](06-工程制图.md)。

单卡可以独立读取术语解释、项目语境和直接来源；要检查核实批次、哈希和更新历史时，需要同时读取 manifest。项目源码不会随卡片自动复制，库内文档链接与需要原工程才能定位的证据路径分别解释。

### 4.4 以 manifest 说明卡片结构

下面是设计字段示意，解释拟议的知识库清单，不是已实现代码或真实生成结果。核实批次和哈希按用户选择保存在 manifest，不出现在单卡示例中。关联的 `术语表.md` 是拟议正式文档。`current` 仅表示该设计声明在示例中的新鲜度，不能解释为相关能力已经实现。

```json
{
  "schema_version": "1.0",
  "id": "k_8d72544a-7af5-4a9b-9c6f-420fc82046bf",
  "term": "manifest",
  "aliases": ["manifest.json"],
  "category": "project_term",
  "context": "km 知识库管理",
  "definition": "记录受管文档、来源记录和内容修订的知识库清单。",
  "project_usage": "用于判断文档更新范围、检查产物一致性，以及恢复中断的更新。",
  "basis": {
    "definition": "document_declared",
    "project_usage": "document_declared"
  },
  "status": "current",
  "articles": [
    {
      "path": "术语表.md",
      "anchor": "manifest"
    }
  ],
  "sources": [
    {
      "kind": "document",
      "path": "docs/devel/design/03-增量更新与质量控制.md",
      "topic": "KnowledgeQuality",
      "supports": ["definition", "project_usage"]
    }
  ],
  "tags": ["knowledge", "metadata"]
}
```

该示例的 `id` 对应文件名为 `k_8d72544a-7af5-4a9b-9c6f-420fc82046bf.json`，直接位于 `docs/official/.cards/`。拟议的库级清单则是 `docs/official/.cards/manifest.json`；两者都属于 JSON，但清单不是术语卡片。

### 4.5 更新、删除与退役

宿主 AI 更新时先核对既有术语、语境与 manifest，延续相同语义身份的 ID。新 ID 遵循 `k_` 加 UUID 的约定，可用宿主已有工具生成并检查已有记录；没有可用方式完成分配或确认旧身份时，保留候选说明，不声称已完成唯一性核对。

UUID 约定不提供自动分配、并行协调或全局唯一性的执行保证。分支汇合或恢复旧记录时仍须核对 ID 与语义是否冲突，不能以标识形式合法代替实际的一致性检查。

| 变化 | 卡片语义 |
|---|---|
| 名称拼写、大小写或文件位置改变，概念和语境延续 | 核实对应关系后保留原 ID，更新名称或来源 |
| 定义或项目用途变化 | 更新相同语义身份的卡片及依据，同时检查关联正文 |
| 名称的含义分裂或被不同概念替代 | 明确区分新旧语义，不强行沿用一个 ID 混合解释 |
| 同一术语新增出现位置 | 补充同一卡片的来源，不按文件数量重复建卡 |
| 一个来源文件删除 | 先检查其它现行引用；文件消失不等于术语消失 |
| 已有证据不足、冲突或无法核实 | 标记 `stale` 并说明缺口，不能继续呈现为已核实的当前解释 |
| 确认术语在当前项目中已无现行用途 | 标记 `retired`，保留身份、历史证据和可追溯引用，撤出默认当前内容 |

过期或退役不抹去旧证据。不能仅为让卡片看起来更新而改写 manifest 中的核实记录，也不能用本轮的未完成候选冒充已经核实的来源。

### 4.6 与 Markdown 和内容修订的关系

正式 Markdown 使用中文标题及无编号中文文件名，直接存放于 `docs/official/`；`README.md` 负责导航。用户已明确卡片可以绑定对应文章，采用 `articles` 数组，关联相关主题文章或术语表章节。架构、流程和规则仍在各自正文解释。

每个关联项以 `path` 保存文档根相对路径，`anchor` 可选且只保存章节锚点标识；没有 `anchor` 时指向整篇文章。一张术语卡可以关联多篇文章，一篇文章可以使用多张术语卡；不能为了每篇文章各建一张重复术语卡。正式绑定前须核对文章和所填锚点存在，候选中的示意路径不能冒充有效链接。

`articles` 表示在哪里继续阅读，`sources` 表示哪些原始资料支持解释，两者职责不同。生成文章不因被绑定就成为独立事实来源。文章更名、拆分或删除时核对关联并更新有效目标；单个文章链接失效不等于术语已经失效或退役，状态仍由原始依据及项目用途判定。manifest 可以按卡片关联整理反向查询，避免另维护一套相互矛盾的人工绑定数据。

术语表的页面格式与正文呈现遵循[生产文档编写规范](04-生产文档编写规范.md)。正文首次出现术语时给出必要解释并关联完整条目；JSON 的身份、批次和字段结构不机械展开为读者正文。

manifest 由宿主 AI 按 workflow 维护文档到术语卡片的最小关联。术语定义或项目用途变化时检查引用它的正文，避免 JSON 已更新而长文仍使用旧含义。`library_revision` 标记本轮文档、卡片和来源记录所对应的内容修订，具体记录及核对方式由增量设计统一维护；字段存在不等于已经执行哈希校验或证明两类内容完全一致。

本模块只要求卡片到文档及原始证据的明确关系，不扩展完整知识图谱，也不设计展示适配器。其它工具可以独立读取现有文件，不改变卡片的事实与路径契约。

### 4.7 验证与实现情况

宿主 AI 按 workflow 核对必填项、枚举、ID 与文件名、引用路径、明确锚点，以及卡片来源与 manifest 更新记录的关联；来源哈希仅在清单实际记录时参与核对。可以使用宿主已有的 JSON 解析或引用查找工具，但 km 不附带校验脚本、执行引擎或依赖 JSON Schema 执行器。

有工具实际解析 JSON 时，记录所用工具、检查范围及实际结果；没有对应工具时，说明仅完成模型阅读检查，不声称通过机器解析或完整协议校验。结构检查不能代替术语语境、真实别名、缩写全称及证据支持范围的语义核对。

语义检查至少覆盖同名异义、一个术语多处使用、来源移动、单一来源删除、术语退役、文档目标与实现不一致，以及通用定义和项目用途来自不同依据的情形。发现来源缺口不能伪造卡片完整性；覆盖不全、校验失败和外部改动冲突沿用增量质量设计的阻断规则。

v0.1 由[术语参考](../../../references/knowledge-cards.md)承载本协议并由 workflow 加载，实施及样例证据归入 T01。解析结果与同会话语义审阅分别记录，不据此宣称自动分配、语义判断或增量更新具有确定性保证。
