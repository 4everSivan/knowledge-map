# 单篇文档编写流程设计

> **created**: 2026-10-15 ｜ **last-change**: 2026-10-16 ｜ **status**: baseline

## 1. 简介

本设计适用于 km v0.1.0。用户于 2026-10-15 明确“0.1 版本的设计暂时定稿，按文档治理流程落地实现”，本组设计据此确认为该版本基线；实现与验收由 T01 记录，设计批准不等于运行能力验收。

本设计补充文档库构建流程中的单篇写作过程，分别说明首次编写和已有文档更新如何从来源分析进入起草、表达修订与事实回查。文档库仍采用“先全局架构，再按专题分批读写，最后统一检查交付”的节奏；本流程嵌入专题批次，不另设用户命令。

用户提出“分析代码 → 文档初版 → 去 AI 味 → 定稿”及“分析代码 → 比对文档差异 → 更新文档 → 去 AI 味 → 定稿”两条流程，并要求参考指定的写作技能进行对抗性讨论。目前已确认表达修订的权限、增量范围和本地英文参考的集成方式，本次整组设计确认为 v0.1 基线，执行文件与检查证据由 T01 落实。

## 3. 规范

### 3.1 已确认的修改权限

“去 AI 味”在 km 中承担表达修订：改善可读性，保留事实、条件、命令、术语和章节锚点；修订前后复核事实。发现内容或结构问题时，返回来源分析或起草阶段，不能借表达修订的名义直接改写技术结论。

更新时只修本次变更涉及的段落及必要上下文，未变部分保持原样。经可靠证据确认没有实质变化的文档直接复用，不能为制造更新记录而重写正文或刷新内容日期。影响范围仍须按增量设计核实，不能将“只修变更部分”解释为“只分析改动行”。

### 3.2 输入、产物与完成边界

单篇写作使用已读取的源码、原项目文档、明确的阅读目的、适用大纲与来源记录。更新另需已有受管文档、变化依据及受影响结论。已有生成文档是比较对象，不能成为证明项目行为的独立来源。

单篇产物是经过检查的文档候选及必要的来源、问题记录。文档候选仍需参加文档库的导航、术语、跨文档一致性、覆盖与冲突检查。单篇“定稿”不能单独触发正式替换；正式集合的写入与恢复边界沿用增量设计。

所有面向 AI 的执行指引使用英文；目标工程文档继续用中文。表达修订不运行正文中的命令，不引入 km 脚本或外部写作服务。本轮所有工作由当前会话处理，不启动 subagents；逻辑上分遍检查不构成独立审阅证据。

### 3.3 v0.1 集成决定

用户已确认采用随 km 维护的本地英文技术适配参考，由 workflow 在表达修订阶段按需读取，不要求使用者安装上游 skill。v0.1 通过单篇参考加载表达修订规则；默认仅对 Markdown 作表达修订，卡片释义与用途在来源和内容核对阶段维护。每批完成相关阅读、内容核对及事实回查后才能交给整库检查。

工程制图及新增输出契约由[工程制图设计](06-工程制图.md)补充，T03 跟踪实施与验收；SVG 位于 `docs/assets/km/`，清单位于 `.cards/diagrams/`，纳入同一整库更新。

## 4. 设计详情

### 4.1 两层流程的关系

<!-- @topic: DocumentAuthoring -->

```text
文档库构建：盘点 → 全局架构 → 专题分批读写 → 整体检查 → 更新交付
                                  │
                                  └─ 单篇写作：分析 → 起草或更新 → 表达修订 → 回查候选
```

外层负责范围、专题次序、文档关系和正式交付；内层负责一篇文档的来源、内容和表达。候选有问题时回到相应写作步骤，不必重新盘点无关专题。公共契约或架构理解发生变化时，重新判断其他候选是否受影响。

T02 将每个业务模块的独立主设计与所需专题纳入同一计划，逐篇采用本文生命周期。单篇完成不表示模块集合完成；模块集合完成也仍需整库统一检查。细读后回填总体摘要与跨模块关系，复杂流程在独立文档维护主要解释，参与模块互链。

### 4.2 初次编写

v0.1 流程为“分析代码与原文档 → 起草并核对来源 → 表达修订 → 事实回查与定稿候选”。来源检查放在起草完成条件中，保留用户提出的四段主流程。

| 阶段 | 关键动作 | 可推进的条件 |
|---|---|---|
| 分析代码与原文档 | 从实际入口、调用关系和项目声明理解主题；确定读者问题、适用范围与未确认事项 | 能说明主要结论由哪些材料支持，区分实现、声明与推断 |
| 起草并核对来源 | 按已确认大纲裁剪正文；核对职责、条件、默认值、异常和结论依据 | 关键结论有对应来源，缺口和冲突未被润色成确定事实 |
| 表达修订 | 在允许范围内消除重复、空泛评价、冗长句式和模型协作口吻 | 技术含义与受保护内容未改变；需要修正的内容问题已返回上一阶段 |
| 事实回查与定稿候选 | 比较修订前后含义，回查关键来源与保护项 | 未发现事实漂移；检查方式、范围与未解决事项可说明 |

先核对草稿，再修表达，避免忠实保留一份本来就有错误的初稿。修订后同时对照修订前草稿与原始来源：只比较两份文字，无法证明初稿本身成立。

### 4.3 更新已有文档

v0.1 流程为“分析当前代码与原文档 → 比对受影响结论 → 更新并核对来源 → 局部表达修订 → 事实回查与定稿候选”。

| 阶段 | 关键动作 | 范围约束 |
|---|---|---|
| 分析当前代码与原文档 | 确认实际变化与依赖影响，读取相应调用方、配置消费者和共享契约 | 分析范围按影响扩展，不只看代码差异行 |
| 比对受影响结论 | 将现有文档的相关结论与当前来源逐项对照 | 区分行为变化、仅引用变化、原先错误及无影响变化 |
| 更新并核对来源 | 修正受影响正文、示例和来源；内容或结构问题在此处理 | 必要时调整大纲并同步引用，保留无关且有效的内容 |
| 局部表达修订 | 只处理已修改段落及理解它们必需的相邻上下文 | 不重新润色整篇，不为统一节奏改动无关段落 |
| 事实回查与定稿候选 | 复核本次更新正确，表达修订没有再改变技术含义 | 检查变更范围、受保护内容及受影响的引用关系 |

代码文本变化不必然带来文档结论变化。可靠确认正文和引用均仍适用时，直接复用；若只需修正来源路径，则更新该引用，不顺带润色整篇。原文档发现独立内容问题时，先定位依据并纳入内容修订范围，再进入表达修订。

仅项目设计文档变化时，更新其目标或声明，保留与当前实现的区别。内容发生实质变化才更新日期；复查批次进入 manifest 等既定记录，不写入读者正文。

### 4.4 表达修订与问题返回

表达修订可以在段内拆分或合并句子，明确已有的动作主体，删去不承载信息的重复与评价。章节拆并、信息重排、术语含义调整和命令修正属于内容或结构工作，先返回分析或起草阶段。

| 发现的问题 | 处理去向 |
|---|---|
| 来源与草稿不符、缺少关键条件、夸大验证范围 | 回到来源分析或内容修订，补读后形成新的待修订草稿 |
| 章节目的混杂、需要拆篇或修改标题锚点 | 回到规划或起草，同步检查导航与卡片文章关联 |
| 表达修订改变条件、数值、否定或确定程度 | 撤回相应表达改动，按来源重新修订并复查 |
| 来源不可读或存在无法解决的矛盾 | 保留候选与问题记录，按增量设计呈现覆盖与校验状态 |
| 没有实际表达问题 | 保持原文，不凑修改次数或套用替换词表 |

问题记录服务于内部回查和实际结果报告，不要求读者阅读逐段润色日志，也不新增每阶段人工批准。JSON 解析或链接检查只能补充相应结构证据，不能宣称证明语义等价。

### 4.6 对抗性样例与验证状态

下列为设计反例，数值和行为仅用于说明检查边界，不是目标工程的实际配置，也不是已运行的测试结果。

| 场景 | 可接受的行为 | 应拒绝的行为 |
|---|---|---|
| “通过执行配置校验来实现对输入配置的检查” | 改为“校验输入配置”，保留动作含义 | 添加来源未支持的校验能力或保证 |
| 原句包含 `enabled=true`、最多 `3` 次 | 保留启用条件、上限与对应动作 | 为简洁删去条件，或把“最多”改成“一定” |
| 草稿声称重试机制保证高可用，来源未支持该结论 | 返回来源分析与起草，修正结论范围 | 只把句子润色得更可信 |
| 默认值从 `30` 改为 `10` | 内容阶段更新受影响结论、示例和用途，再局部修订表达 | 表达阶段擅改数值，或顺带重写所有稳定章节 |
| 文档注明未运行目标环境测试 | 保留验证范围与未知项 | 改成目标环境已验证或功能不存在 |
| 章节被卡片 `articles` 引用 | 表达阶段保留标题和锚点 | 润色标题后留下失效卡片关联 |

本版本已创建技能入口、workflow 和单篇/表达修订参考，T01 记录检查与隔离样例。项目治理检查只能验证文档登记、结构等对应范围，不能证明模型每次都能保持语义等价或达到所谓“人类写作分数”。

后续实施应使用有明确来源的初稿和更新样本，检查真实变化范围、条件与结论保留、错误草稿返回路径、无变化复用以及文章和术语关联。未执行的样例不得登记为通过；修订前后复核由同一会话完成时如实说明。
