# 文档库与命名规范

> **created**: 2026-10-15 ｜ **last-change**: 2026-10-15 ｜ **status**: baseline

## 1. 简介

本设计适用于 km v0.1.0。用户于 2026-10-15 明确“0.1 版本的设计暂时定稿，按文档治理流程落地实现”，本组设计据此确认为该版本基线；实现与验收由 T01 记录，设计批准不等于运行能力验收。

本设计定义 km 生成文档的内容边界、存放位置、中文命名、导航和引用约定，供宿主 AI 按本版本 skill workflow 文件生成、检查和更新文档时使用。

用户已明确当前专注文档生成：Markdown 直接放在 `docs/official/`，JSON 放在其 `.cards/`；不提供人工补充目录，不生成静态网站。生产文档使用中文文件名和中文标题，去掉排序数字前缀。

本文件是研发设计，遵循项目治理四章大纲和设计目录编号。这里的无编号命名约束面向 km 在目标工程生成的生产文档，不重命名本项目既有治理资产。v0.1 的执行规则由根目录 workflow 与参考文件承载；km 不提供或依赖执行脚本、独立执行引擎或脚本产物协议。

## 3. 规范

### 3.1 产物与范围

| 项目 | 约定 |
|---|---|
| 文档根 | 固定为目标工程的 `docs/official/` |
| Markdown | 直接存于文档根，按内容需要拆分；不增设生成文档层或人工补充层 |
| JSON | 全部位于 `docs/official/.cards/`，术语卡直接使用 `<id>.json` |
| 阅读入口 | `docs/official/README.md`，正文标题为“项目知识库” |
| 内容来源 | 项目自有代码、配置、已有项目文档和有明确依据的必要参考 |
| 输出边界 | 不生成网站，不引入展示框架或服务，不收录生产目录中的手写补充 |
| 原项目资产 | 原位读取，不迁移已有文档、源码、测试和构建输入 |

生成文档按实际项目内容选择，不以填满固定章节或数量作为完成目标。无数据库、HTTP 服务或守护进程的项目不生成相应的虚构能力说明。

### 3.2 命名规则

| 规则 | 要求与例子 |
|---|---|
| 中文语义名称 | 文件名直接说明主题，例如 `系统总体设计.md`、`服务启动流程.md` |
| 无排序前缀 | 不使用 `00-`、`01-` 等位置编号；阅读顺序由导航表达 |
| 标题一致 | 一级标题与文件名主题一致，保留完整、清楚的中文含义 |
| 用途准确 | 完整设计、运行流程、参数参考和故障处理分别命名，不统一套用“设计方案” |
| 范围明确 | 同一目录需要区分模块时，使用 `模块名-主题.md`，例如 `任务调度-重试机制.md` |
| 名称稳定 | 正文或阅读顺序变化时保留路径；真正更名时同步所有引用 |
| 无修订标签 | 不在文件名附加“最终版”“最新版”、修改日期或文档迭代号 |
| 保留真实标识 | 术语中的数字、大小写或产品名原样保留，例如 `OAuth2认证流程.md` |
| 入口例外 | 沿用已约定的 `README.md`；JSON 文件使用协议规定的标识和保留名称 |

普通中文词自然连写，不逐词加入连字符。避免 `说明.md`、`其它.md` 等缺少主题的泛称。模块名称和术语采用工程中的实际用词，不在每轮生成时随意更换译名。

### 3.3 事实与写作约束

文档解释当前静态实现、原文档声明和未确认问题，各自注明来源。不能从文件存在推断它已接入主链路，不能把设计目标写成已实现事实，也不能把未运行的测试写成通过证据。

读者正文按任务和主题组织：系统设计说明边界与协作，流程说明入口、分支与结束条件，参考说明契约和默认值，排障说明现象、定位依据与实际支持的处理方法。生成文档不一律套用本研发设计的四章结构。

用户已确认的页面格式、正文标题无章节序号、Markdown 元素规则、分类大纲和来源呈现统一由[生产文档编写规范](04-生产文档编写规范.md)维护。本文保留文档库内容边界、命名和引用职责，不重复维护完整编辑规范。

宿主 AI 遵循 workflow 文件，使用宿主已有的读取、编辑、搜索和检查工具完成工作。检查结论以实际工具能力和读取范围为限，不假定存在 km 自动校验器或确定性更新机制。

## 4. 设计详情

### 4.1 内容模型

<!-- @topic: KnowledgeLibrary -->

| 内容类别 | 回答的问题 | 典型文档名 |
|---|---|---|
| 项目概览 | 工程解决什么，应该从哪里读起？ | `README.md`；内容较长时再拆 `项目概览.md` |
| 系统总体设计 | 边界、模块、依赖和数据流如何组织？ | `系统总体设计.md` |
| 模块设计 | 某领域的职责、契约和规则是什么？ | `任务调度设计.md`，按实际模块命名 |
| 核心流程 | 一次运行从哪里进入，如何完成或退出？ | `服务启动流程.md`，按实际流程命名 |
| 接口与数据 | 如何调用、交换和保存数据？ | `接口参考.md`、`数据模型.md` |
| 配置与运行 | 参数如何生效，如何按现有入口运行？ | `配置参考.md`、`运行指南.md` |
| 业务约束 | 关键判断、不变量和边界是什么？ | 按实际业务主题命名，必要时独立成篇 |
| 开发与验证 | 如何扩展，已有检查验证什么？ | `开发指南.md`、`测试说明.md` |
| 术语解释 | 专业名称或独有名称在项目中是什么意思？ | `术语表.md`，关联 `.cards/` 下的 JSON 术语卡 |
| 来源与缺口 | 哪些内容已核实，哪里仍有冲突或未覆盖？ | `来源与待确认项.md` |

上表是内容候选和命名例子，不是全部必须创建的文件。总体设计与系统架构内容重叠时先保持一篇；只有不同读者任务或规模需要时才拆分。

每篇先确定主要阅读目的，再从编写规范选择并裁剪大纲。内部机制说明与指导人的操作分别组织；快速入门围绕一条完整体验路径，技术参考围绕可检索的契约。项目概览和业务约束等内容按实际主题归入适用文类。

### 4.2 存放布局

```text
docs/official/
  README.md
  系统总体设计.md
  任务调度设计.md
  服务启动流程.md
  配置参考.md
  术语表.md
  .cards/
    k_<uuid>.json
    config.json
    manifest.json
    last_attempt.json
    runs/<run_id>/
  .staging/<run_id>/
```

正式 Markdown 直接存放于文档根；每个术语的 JSON 直接位于 `.cards/`，不再增加卡片子目录。JSON 候选、检查结果和恢复记录也位于 `.cards/runs/<run_id>/`；Markdown 候选和恢复副本位于 `.staging/<run_id>/`。运行目录按需创建，不预建空批次。

`config.json` 只用于覆盖扫描范围、文档语言和写作偏好等默认值，首次调用不要求用户填写。宿主 AI 按 workflow 维护 `manifest.json` 中的文件身份、来源记录、内容修订与关联；它是更新所用的 JSON 资料，不是脚本返回值或执行引擎状态。运行记录和正式知识内容的有效性边界见增量设计。

### 4.3 导航与引用

`README.md` 按读者任务分组链接真实存在的文档。标题可以调整；不因章节排序或措辞润色批量改名。新增和拆分文档时，同时更新导航、关联卡片和 manifest 中的引用。

| 引用位置 | 路径基准 |
|---|---|
| Markdown 链接 | 当前 Markdown 所在目录 |
| 术语卡关联文章路径 | `docs/official/` 根目录，可按卡片协议关联明确章节锚点 |
| 术语卡 `sources.path` | 目标工程根目录 |
| manifest 受管文件路径 | `docs/official/` 根目录 |

被长期引用的章节使用明确、稳定的锚点。命名调整须核对文件路径、Markdown 链接、卡片文章关联和登记记录；不能只修可见导航而留下悬空引用。

### 4.4 输入与输出隔离

扫描原项目 `docs/` 时只排除 `docs/official/` 整个输出子树，其余项目文档照常读取。可选配置由宿主 AI 按 workflow 单独读取；生成正文、卡片和运行记录均不作为新的项目事实来源。

只管理 manifest 明确登记的生成文件。输出位置已有不明文件，或受管文件出现外部改动时，保留原文件并报告冲突；不自动吸收修改或静默覆盖。处置与恢复规则见增量设计。

### 4.5 验证与实现情况

验收需要检查：产物路径正确，生产 Markdown 无排序前缀，文件名与标题主题一致，导航指向真实文件，卡片与正文的引用基准一致，排除规则不会漏掉其它项目文档。

这些检查由宿主 AI 按 workflow 执行，能使用现有工具检查时记录真实结果；没有相应工具时说明模型审阅的范围与未核对项，不把未执行的解析、链接扫描或哈希比较写成通过。主题选择与表述准确性仍需对照来源审阅。

v0.1 已通过英文写作参考承载本规则；样例与实际检查由 T01 和 tests/acceptance.md 记录。不以指引存在或结构检查冒充自动校验保证。

### 4.7 参考资料

- 用户会话中的目录与命名选择：文档直接位于 `docs/official/`，JSON 位于 `.cards/`，中文文件名和中文标题，无排序数字前缀。
- 用户关于执行方式的澄清：通过 workflow 文件更新，当前项目不用任何脚本。
- [Google 文件命名指南](https://developers.google.com/style/filenames)：名称明确、约定一致；其 ASCII 字符约定按本项目已选择的中文命名调整。
- [Google 标题指南](https://developers.google.com/style/headings)：标题体现概念说明或操作任务的实际用途。
- [GitHub Docs 文件名约定](https://docs.github.com/en/contributing/writing-for-github-docs/using-yaml-frontmatter#filenames)：文件名和文章标题关联。本项目采用相应的中文主题约定。
