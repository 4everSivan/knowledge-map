# knowledge-map 系统总体设计

> **created**: 2026-10-15 ｜ **last-change**: 2026-10-15 ｜ **status**: baseline

## 1. 简介

本设计适用于 km v0.1.0。用户于 2026-10-15 明确“0.1 版本的设计暂时定稿，按文档治理流程落地实现”，本组设计据此确认为该版本基线；实现与验收由 T01 记录，设计批准不等于运行能力验收。

knowledge-map 是一个可复用的技能项目，拟以 `km` 为对外技能名。用户在目标工程调用 `$km`，由宿主 AI 阅读自有代码及已有项目文档，生成可追溯的中文 Markdown 文档库与 JSON 术语知识卡片。源码或项目文档变化后，重复同一调用更新受影响知识。

已讨论确定的产品边界是：只生成知识文档，Markdown 直接放在 `docs/official/`，JSON 集中在 `docs/official/.cards/`；卡片解释专业术语和项目独有名称；生产文档采用中文文件名与中文标题，去掉排序数字前缀。技能通过 workflow 文件约束宿主 AI 完成更新，km 本身不提供或依赖执行脚本。当前范围不包含静态网站或人工补充内容。

本组设计采用项目治理的四章大纲，并已确认为 v0.1 基线。实现载体为技能入口、英文 workflow 与按需参考；设计批准、结构检查、样例演练和技能宿主验收分别记录。

## 3. 规范

### 3.1 产品要求

| 编号 | 要求 | 约束 |
|---|---|---|
| R01 | 一个默认调用完成生成和更新 | 用户无需手动执行扫描、生成、检查等子命令 |
| R02 | 默认当前工程、首次零配置 | 只在需要覆盖范围或写作偏好时提供可选配置 |
| R03 | 中文文档和结构化术语卡 | 两类输出来自同一次核实的工程事实与来源 |
| R04 | 重复调用识别实际变化 | 覆盖未提交修改、未跟踪自有文件和非 Git 工程；不只比较 commit |
| R05 | 结论有据、覆盖明确 | 区分代码支持、文档声明、参考依据、推断和未读取范围 |
| R06 | 固定输出位置 | Markdown 直接位于 `docs/official/`，所有 JSON 位于其 `.cards/` |
| R07 | 术语卡片有项目语境 | 解释专业名称、缩写和独有名称；流程、操作和完整规则写入 Markdown |
| R08 | 中文语义命名 | 无排序前缀，路径稳定；入口沿用 `README.md`，JSON 使用协议规定名称 |
| R09 | 保护已有资产 | 原源码和文档原位读取，只替换已登记且未出现外部修改的生成产物 |
| R10 | 失败可恢复 | 不把部分覆盖、校验失败或冲突结果提交为完整知识库 |
| R11 | workflow 文件驱动 | 宿主 AI 按流程描述使用已有工具完成工作；km 不引入脚本或流程执行引擎 |
| R12 | 统一写作格式、按文类组织 | 简洁篇首、无章节序号、按阅读目的选择大纲，引用与未知范围如实呈现 |
| R13 | 英文 workflow 执行描述 | 面向 AI 的阶段动作、完成条件和异常指引使用英文；生成的中文文档沿用既定语言 |
| R14 | 业务模块逐项独立覆盖 | 所有已识别业务模块均有独立主设计；复杂模块按需拆专题，复杂跨模块流程独立成文，分别检查识别与文档集合覆盖 |

### 3.2 范围与授权

技能使用当前宿主的 AI 理解能力，不要求另配模型 API Key、向量数据库或在线知识服务。workflow 文件规定每阶段的输入、动作、产物、检查与异常处理，由宿主 AI 阅读并遵循；它是执行指引，不是交给程序运行的工作流引擎。AI 使用宿主已有的搜索、文件读取、差异查看、编辑等工具完成扫描和更新，不新增扫描、生成、校验或写入脚本。

workflow 面向 AI 的执行描述使用英文，包括阶段动作、输入输出说明、完成条件和异常处理；项目实际名称、代码标识和引用路径保持原样。研发设计与人类讨论继续使用中文，生成的文档标题、文件名及正文遵循已确认的中文规范。JSON 字段名采用英文，术语和解释保留目标工程及读者所需的语言。

结构与内容检查由 AI 按规则逐项完成；宿主已有工具能够解析 JSON、核对链接或取得内容摘要时，使用实际结果补充证据。未执行的工具检查如实记录，不能把模型审阅描述成程序校验。现有 ad-flow 校验器仅用于本项目的研发治理，不分发给 km 的使用项目，也不是调用 km 的运行依赖；本轮不删除或改造既有治理资产。

生成器读取项目资料，资料中的命令不成为执行指令。业务工程的构建、测试、启动、部署和外部服务操作不由知识扫描默认触发。原有测试可以作为分析输入，未实际运行就不能声称通过。

当前产品范围只有知识生成、更新和校验。展示、在线问答、多仓库聚合及完整知识图谱留待实际需求驱动；不为这些能力预设依赖或适配层。

### 3.3 v0.1 执行约定

v0.1 使用根目录 `SKILL.md` 和 `workflow.yaml`，按需读取 `references/` 下的文档规则。读写节奏为“先全局架构，再按专题分批读写”，最后统一检查交付。单篇流程区分初次与更新；表达修订前后复核事实，更新只修变更部分及必要上下文，无实质变化时直接复用。

卡片和清单协议均固定为 `1.0`，卡片文章绑定使用 `articles` 数组。清单以 `documents` 键和 `cards[*].path` 登记受管文件，按卡片 ID 集中核实记录，字段说明见[状态契约](../../../references/library-state.md)。v0.1 默认只对 Markdown 运行表达修订，卡片通过来源与内容审阅保持准确。

专题按真实职责及阅读问题划分；每批必须完成相关取证、候选内容核对、表达修订与事实回查。未完成范围写入最近尝试记录，下次先核对来源和中断写入再续读。具体阶段输入、动作、产物、完成条件与返回路径见[workflow](../../../workflow.yaml)。实施由 T01 登记，不能因基线定稿而直接标记任务完成。

业务模块分层规则由 T02 补充：总体保留主干协作、全局约束及逐模块摘要和主设计链接；每个业务模块均独立主设计，复杂细节按需拆专题；复杂跨模块流程独立维护完整说明，参与模块展开自身职责并互链。模块按实际职责与契约识别，模块主文件存在不替代其所需专题完成。具体识别、计划与覆盖规则见[文档库设计](01-文档库与命名规范.md)。

## 4. 设计详情

### 4.1 系统职责与关系

<!-- @topic: KnowledgeMapWorkflow -->

```text
用户调用 km
  → 宿主 AI 加载 workflow 文件与项目规则
  → 工程输入与现有知识状态
  → 宿主 AI 理解代码、文档与术语
  → Markdown 文档与 JSON 术语卡候选
  → 按 workflow 核对结构、覆盖和来源
  → 更新受管知识产物并返回文档入口
```

上图只说明职责关系。以 `workflow.yaml` 描述阶段顺序和完成条件，写作、状态及术语规则按需引用独立参考文件；这些文件供宿主 AI 阅读，不交给程序引擎执行。

英文执行描述示例为：`Establish the overall architecture before reading and drafting by topic. Treat generated files as outputs, not independent evidence. Write the final documents to docs/official/.` 该示例体现语言与边界，实际动作以版本内 workflow 为准。

| 职责 | 主要承担者 | 输出 |
|---|---|---|
| 文件盘点与变化识别 | 宿主 AI 使用现有搜索、文件和差异工具 | 输入清单、可核实的变化及未知范围 |
| 工程理解与内容规划 | 宿主 AI | 真实边界、入口链路、适用文档和术语解释 |
| 文件与身份管理 | 宿主 AI 核对既有清单与卡片 | 稳定路径、沿用的术语 ID 和来源登记 |
| 结构检查 | 宿主 AI；可用时使用已有解析或核对工具 | 字段、引用、导航和覆盖核对结果及证据边界 |
| 语义复核 | 宿主 AI | 结论是否被来源支持，冲突与不确定项 |
| 写入与报告 | 宿主 AI 使用文件编辑工具 | 文档、卡片、真实进度和实际检查结果 |

建议内部顺序为“盘点 → 规划 → 阅读取证 → 生成候选 → 检查修订 → 更新交付”。每阶段须声明输入、动作、产物、完成条件和异常去向；AI 核对条件后推进，用户仍只调用一次。候选、覆盖记录和来源关联服务于本轮写作与检查，不构成 AI 向脚本交接的协议。批次和恢复规则由 workflow 及状态参考维护。

用户已确认阅读与写作采用以下节奏。该选择约束内部执行方式，不代表其它 workflow 细则已经批准。

| 环节 | 已确认的执行方式 |
|---|---|
| 全局架构 | 先盘点工程并核实系统边界、实际入口和核心协作，建立后续专题的共同背景 |
| 专题分批读写 | 按专题阅读相关来源、记录依据并生成候选；据取证结果调整页面范围和适用大纲 |
| 统一检查交付 | 分批产出仍为候选，满足整体覆盖、质量及冲突核对条件后再更新正式集合 |

暂定文档计划服务于阅读，不因先列出主题就将其视为事实。取证可以调整文类、大纲和拆并页方式；已确认的编写规范继续作为约束。专题划分依实际工程裁剪，完成条件及续读记录按 workflow 和状态参考执行。

专题批次内按单篇区分初次编写与更新。建议在起草或更新后核对来源，再进行表达修订，最后回查事实形成候选；只有外层整体检查满足交付条件后才正式替换。英文表达修订参考已由单篇流程按需接入 workflow。

源码理解从真实入口与调用关系出发。CLI 解释声明入口和实际被调用代码；守护进程解释线程、协调循环、后台任务和关闭路径。模块文件存在不等于运行接入，设计文档声明不等于已经实现。

### 4.2 输入输出边界

输入包括工程自有源码、清单、配置、测试和原项目文档。默认排除依赖、构建产物、备份、明显凭证和输出子树；扫描原有 `docs/` 时仅排除 `docs/official/`，保留其它原项目文档。

输出入口固定为 `docs/official/README.md`。生产 Markdown 直接放在该目录，所有术语 JSON、配置、manifest 和运行状态归入 `.cards/`。原有生成文件不再作为新的项目事实来源，配置通过专门通道读取。

本项目研发设计继续位于 `docs/devel/design/`，沿用现有编号和四章大纲；上述无编号命名规则面向目标工程的生产文档。

### 4.3 关键契约

- 文档组织、命名和路径基准以 [文档库设计](01-文档库与命名规范.md) 为准。
- 页面格式、文类大纲、正文编辑和来源呈现以已确认的[生产文档编写规范](04-生产文档编写规范.md)为准。研发治理文件继续采用本项目四章大纲。
- 单篇初次与更新、表达修订的已确认权限及本地英文参考集成方式见[单篇文档编写流程](05-单篇文档编写流程.md)。表达修订不能静默修正事实或结构问题。
- 术语身份、字段和语境以 [术语卡片设计](02-术语知识卡片设计.md) 为准。同词异义按语境区分，同一概念的多处来源归入同一卡片。
- 输入核对、增量失效、partial 续跑、冲突保护和恢复以 [增量与质量设计](03-增量更新与质量控制.md) 为准。没有实际工具证据时不能编造内容摘要、完整快照或无变化结论。
- Markdown 和卡片共享核实后的来源。卡片释义或用途变化时检查相关正文，不能各自生成互相矛盾的内容。
- 格式检查不证明工程理解完整或生产行为成立。来源不明或存在冲突时明确呈现，不能用模板内容填补事实缺口。

### 4.4 实现与验证状态

v0.1 已创建 [技能入口](../../../SKILL.md)、[英文 workflow](../../../workflow.yaml) 与五份配套参考。入口、范围盘点、架构理解、专题写作、整库核对、正式更新及结果报告均有执行指引；不建设扫描器、运行脚本或程序执行层。

T01 记录初版实现，T02 记录业务模块分层规则的实施分支、检查与验收证据，实际进展以[任务总账](../task/index.json)为准。设计基线不证明 AI 执行具有确定性，也不证明目标业务软件通过运行或生产验收。

开发验证采用现有技能基础检查、YAML/JSON 解析、治理检查与隔离样例演练；具体范围和限制见[验收说明](../../../tests/acceptance.md)。未获实测的宿主发现、`$km` 触发及 `/km` 适配如实保留，不以文件存在冒充入口已注册。
