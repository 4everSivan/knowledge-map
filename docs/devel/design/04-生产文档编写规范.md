# 生产文档编写规范

> **created**: 2026-10-15 ｜ **last-change**: 2026-10-25 ｜ **status**: baseline

## 1. 简介

本设计适用于 km v0.1.0。用户于 2026-10-15 明确“0.1 版本的设计暂时定稿，按文档治理流程落地实现”，本组设计据此确认为该版本基线；实现与验收由 T01 记录，设计批准不等于运行能力验收。

本设计规定 km 生成 Markdown 文档时的阅读路径、页面格式、中文表达、文类大纲和来源呈现方式。目标是让读者能快速判断文档是否适用，找到所需解释或操作，并了解结论的依据与边界。

设计来源是本次会话中的资料研究与写作规范讨论。用户以“确认，落地这些设计后继续讨论”批准落地本写作规范，因此本文件作为已确认的设计基线；该次确认只批准写作规则；本次 v0.1 定稿另行批准整组设计。现有检查结果、实现与运行验收证据分别记录。

生产文档继续采用中文文件名、中文标题和无排序前缀命名，Markdown 直接位于 `docs/official/`，全部 JSON 位于 `docs/official/.cards/`。本规范不引入网站、执行脚本或人工补充目录。本文件属于研发治理设计，保留治理编号和四章大纲；生成的生产文档按读者任务选用大纲。

## 3. 规范

### 3.1 适用范围与职责

本规范约束 km 在目标工程生成的生产 Markdown。目录、文件身份及引用基准由文档库设计规定；术语语义和 JSON 字段由卡片设计规定；更新、冲突与恢复由增量设计规定。本文件定义这些内容面向读者时怎样组织和表达，不另建执行机制。

宿主 AI 按本版本 workflow 使用已有搜索、读取和编辑工具落实规范。km 不提供或依赖执行脚本、独立执行引擎、网站渲染器或专用 Markdown 扩展。`docs/official/` 中的 Markdown 保持平铺，JSON 继续集中在 `.cards/`，不因阅读分组增加文档子目录。

### 3.2 阅读目的与事实约束

每篇文档先确定读者要理解的概念、要完成的任务或要查询的契约，再选择文类和范围。只生成工程实际适用且有来源的内容，不以固定文件数、完整目录或章节数量作为交付目标。

结论以实际读取的源码、配置和已核实项目文档为依据，区分当前静态实现、原文档声明和推断。外部资料支持通用定义或写作方法，不能代替本项目行为的证据。设计目标、当前接线、实际运行和人工验收分别表述。

历史技术选型理由只引用已有设计或决策记录，不从当前代码倒推当时动机。性能、容量、可用性和测试结果只有对应证据时才能作为实测结论；代码结构、算法特征和测试文件存在均不自动证明这些结果。

### 3.3 默认编写约定

- 采用基础 Markdown 和常用表格语法，保持源文可读，不依赖特定主题、HTML 排版或折叠组件。
- 每篇只有一个一级标题；设计文档正文采用连续的二、三级编号，如“1. 目标”“2.1 功能点”，其它文类按阅读目的组织且默认不编号；文件名继续不加排序前缀，标题不使用装饰图标。
- 篇首依次提供标题、简短导语和确实影响理解的适用范围；批次、哈希、扫描计数等管理信息保留在 `.cards/`。
- 中文正文使用统一术语和标点；代码、参数、路径和产品名称保留真实拼写，不随意翻译或改大小写。
- 设计文档导语后提供普通 Markdown 篇内链接目录，至少覆盖全部二级章节；复杂功能可继续列三级入口。文章关联由 README 导航与 `.cards/` 维护，正文遵循单篇自包含规则。
- 文档只维护最后更新日期，不独立递增文档版本；内容发生实质变化时才刷新日期。单纯复查不改日期，核对批次由 `.cards/` 记录。
- 可选章节无适用事实时省略。必要信息无法确认时说明缺失范围、原因和影响，不生成空章、占位表格或反复“待补充”。

以上具体格式与裁剪方式是本项目采用的规则；参考资料提供原则和覆盖思路，不表示这些来源采用了相同的中文命名、目录或元数据协议。

工程制图及新增输出契约由[工程制图设计](06-工程制图.md)补充，T03 跟踪实施与验收；SVG 位于 `docs/assets/km/`，清单位于 `.cards/diagrams/`，纳入同一整库更新。

## 4. 设计详情

### 4.1 文档库阅读路径

<!-- @topic: KnowledgeWriting -->

`README.md` 是知识库入口，按读者目的组织真实存在的文档，而非照搬文件排列或源码目录。每组用简短说明帮助读者选择入口；没有相应内容的分组不预建。

| 阅读目的 | 适用内容 |
|---|---|
| 了解工程 | 项目概览、系统定位、边界与总体结构 |
| 理解实现机制 | 模块设计、核心流程、业务规则 |
| 完成具体任务 | 快速入门、安装运行、操作指南 |
| 查询准确契约 | 配置、接口、数据参考 |
| 定位问题或解释名称 | 故障排查、术语表 |

普通文章在本篇说明阅读所需的概念、前置条件、契约和机制，不提供“相关文档”或“上一篇”“下一篇”。术语首次出现时给出必要解释，不能要求读者跳到术语表后才能理解本篇。

“服务启动流程”解释组件内部如何协作；“启动服务”指导读者执行操作。二者分别满足理解机制和完成任务的需要，并各自保留本篇需要的前提与解释。阅读目的区分借鉴 Diátaxis；文档分组与中文名称采用本项目规则。

#### 单篇自包含与参考文献

C006 根据用户“如果有引用内容则直接搬过来在文章中使用，参考文献只有当使用了互联网资料才写”的要求调整生产正文；本规范及其它研发治理文档、技能参考的导航不属于生产正文。

除知识库入口 `README.md` 外，每篇 `docs/official/` 文章均应独立完整。正文、表格、脚注及篇末不链接其它文章、原项目文档或源码，也不以无链接的“详见某文档”代替解释。需要借用的定义、契约、步骤、约束、案例与结论，按当前主题融入本篇，并对照原始来源核实；不能只删除跳转而保留内容缺口。只纳入理解本篇所必需的内容，不整份复制无关文档；必要复述允许存在，更新时从同一原始依据检查各篇的一致性。

`README.md` 可导航至本库真实存在的文章。普通文章可使用篇内锚点、目录和普通 Markdown 嵌入的工程 SVG；这些资源不能包装为跳转到其它文档的入口。正文仍可用行内代码呈现解释所需的文件路径、符号与命令。总设计与独立详设继续分别生成，其主题、来源和章节映射保存在 `.cards/` 工作计划中，正文不要求互链。

只有本篇确实使用已查阅的互联网资料时才生成“参考文献”，列出标题、实际 URL 及所支持的内容；正文同时解释所用内容，引用用于归属与追溯。互联网地址不能作为绕过规则的跳转：在线托管的本项目文档、源码与同库文章仍是项目来源，不转成外部参考文献。未使用互联网资料时，连同目录项省略整章，不写空章、“无”或“未使用”；非设计文章同样适用。文章引用与查阅记录逐篇对应，不能把只用于技能写作方法或其它文章的资料列入本篇。

完整本地来源关联及结论支持关系保留在 `.cards/`，不以读者正文中的“依据”链接清单承载。来源冲突、缺失与适用条件仍在受影响结论附近说明。新增的 `article_self_containment` 和 `bibliography_usage` 必需检查分别验证单篇内容与引用策略、互联网资料的实际使用；结构扫描与语义审阅分别记实。

### 4.2 页面格式与标题

默认页面顺序为“标题 → 导语 → 必要范围 → 正文 → 按需参考文献 → 最后更新”，各部分以实际需要取舍。

| 页面部分 | 编写要求 |
|---|---|
| 标题 | 唯一 H1，准确说明主题，与文件名主题一致，不附加排序号、图标或修订标签 |
| 导语 | 直接说明本篇回答的问题或完成后的结果，避免重复标题和逐项介绍目录 |
| 适用范围 | 版本、平台、角色或前置条件影响结论时明确展示；不为形式填满字段 |
| 页内目录 | 设计文档提供覆盖全部二级章节的普通链接目录，长篇补充必要功能入口；其它长文按需要提供，不使用 `[TOC]` |
| 正文 | 以 H2、H3 展开，先说明关系、规则或结论，再进入细节；必要时继续细分但不跳级 |
| 参考文献 | 仅列本篇实际使用的互联网资料；未使用时连同目录项省略 |
| 更新时间 | 只反映正文内容的实质更新，不把每次扫描或复查时间写成内容更新 |

概念标题采用清晰的名词短语，例如“配置优先级”；任务标题采用动宾短语，例如“启动服务”。同级标题表达相近层次的内容，避免笼统的“其它”“相关内容”。设计正文按 4.5 的文类大纲连续编号，目录标题、H1 和文件名不编号；操作步骤另用有序列表。

被术语卡或其它页面长期引用的章节沿用文档库设计的稳定锚点规则。修改标题或拆分文章时核对篇内目录与锚点、README 导航、卡片文章关联和受管记录，不只修改可见导航。

### 4.3 中文表达与 Markdown 元素

正文使用直接、具体的中文，明确动作主体、条件和结果。每段围绕一个要点展开，先给读者需要的结论，再说明原因、边界和例外。缩写首次出现时仅在有依据的情况下解释全称；不同名称只有来源证实等价时才互作别名。

句子按表达重心选择主语，读者应能判断每个动作由谁发出、作用于什么对象；动作归属清楚时允许省略主语，执行者变化时重新点明。用具体动词和对象描述行为，以一件事为句子重心；相关动作可以按真实先后顺次表达。条件置于受其约束的动作之前，保留必要条件与充分条件的区别、先后顺序和例外。明确的边界直接写“不接受什么”“不改变什么”，保留原文真实的不确定性与建议强度。

起草阶段依据来源写清适用的成功、失败及最终状态。表达修订阶段只改句子，保留原有标题、分节、段落与技术含义，不因“结果写全”而增加来源未支持的状态、因果或保证。营销形容词和空泛评价改为已有事实；无事实可替换时返回内容核对。详细句子规则和中文正反例集中在[表达修订参考](../../../references/technical-editing.md#sentence-construction)，初次写作与增量更新均在内容核对后的独立阶段执行，随后回查事实。

不同元素分别承载适合的信息，避免把整篇说明拆成表格或条目。

| 元素 | 适用内容 | 编写要求 |
|---|---|---|
| 段落 | 原理、职责、因果关系与边界 | 保持连续解释；段落之间形成清楚的承接关系 |
| 无序列表 | 并列职责、条件或注意事项 | 条目句式和粒度相近；没有先后关系时不编号 |
| 有序列表 | 按顺序执行的动作 | 每步说明动作；必要时先交代操作位置、给出结果检查点 |
| 表格 | 参数、字段、条件和同维度比较 | 单元格保持简短；长段解释移到表外，不依赖宽表承载论述 |
| 代码块 | 命令、配置、代码片段、文本输出 | 标注适合的语言；解释上下文和占位值；只保留当前主题需要的片段 |
| 行内代码 | 标识符、参数、路径和枚举值 | 保留真实拼写，不用作一般中文的强调样式 |
| 提示块 | 易遗漏的补充或确有风险的动作 | 少量使用；必要前提放在相关步骤之前，以普通引用加文字标签即可 |
| 图示 | 模块关系、跨组件时序、状态变化 | 只在帮助理解时加入，说明图的边界，正文保留关键结论 |

命令来自工程实际入口、配置或既有运行文档。需要替换的值先说明含义，不填真实凭证。预期结果明确标为预期；实际输出仅在确实执行后引用，并保留相关环境和范围。生成操作文档本身不要求自动运行部署或业务命令。

正式工程图使用普通 Markdown 图片引用静态 SVG；按[工程制图设计](06-工程制图.md)触发必要图，先核对语义清单再绘图，实际验证文章内显示与独立 SVG。图外保留主要解释与范围说明；不增加网站或 km 运行脚本。表格、提示和步骤的使用分别借鉴 Google 与 Microsoft 指南；中文表达借鉴 Ant Design 的一致和直接原则，不机械套用界面文案的省略方式。

### 4.4 专业呈现与版式一致性

生成文档应读起来像项目自身维护的正式技术文档：面向维护者和集成者，语气中性、陈述明确，整库版式一致。本节由 C001 增补，约束读者可见的呈现方式，不放宽 4.6 的证据与限制规则。

**读者语域。** 现行行为使用一般现在时的陈述句，不使用“我们”，操作步骤直接使用祈使句。不使用感叹号、反问、宣传性形容词、强调副词或表情符号。正文不叙述生成过程：“本轮”“本次生成”“经分析”“未读取到”“已核对”、运行批次、检查结果、样例或演练等字样属于 `.cards/` 与运行报告，不进入生产文档。

**证据状态集中表述。** 整库的依据类型在 `README.md` 导语中说明一次；单篇只在依据类型影响本篇结论时，于导语或适用范围中说明一次。正文用领域语言陈述事实：相关源码范围已完整阅读时直接写“当前实现不提供持久化”；范围未读完时在对应结论处写明范围和原因。具体结论的不确定性只在该结论处说明一次，不在各段末重复“未经运行验证”。

**统一页面骨架与标签。** 下例展示非设计文章的公共格式；设计文章在导语后增加目录，正文采用 4.5 的分类章节，仅在使用互联网资料时增加“参考文献”。

```markdown
# <与文件名主题一致的标题>

<导语：1~3 句，说明本篇回答的问题与核心结论>

<适用范围：仅在影响结论时提供>

## <正文章节>

<直接说明本篇所需的规则、处理过程与边界；本地来源关联记录于 .cards/>

最后更新：YYYY-MM-DD
```

| 用途 | 唯一写法 |
|---|---|
| 本地来源关联 | 记录于 `.cards/`；正文保留解释及必要标识符，不插入来源链接清单 |
| 补充说明 / 风险提示 | `> **说明**：` / `> **注意**：`，不使用其它提示标签 |
| 互联网引用 | 正文解释所用内容，以篇内引用指向按需“参考文献”；每项列标题、实际 URL 和支持内容 |
| 更新日期 | 全篇最后一行 `最后更新：YYYY-MM-DD` |
| 图稿 | 导语句 → 图片 → `图：<图名>。<范围>` → 对图中要点的正文解释；H1 不取图名 |

**最低实质内容。** 每篇至少包含导语和一个有实质内容的正文章节，图、表或链接清单都不能单独构成一篇文章。

| 文类 | 至少说明 |
|---|---|
| 知识库入口 | 以“<项目名> 知识库”为题；导语说明覆盖范围和依据；按阅读目的分 H2 组，按阅读路径排序，每个链接附一句说明 |
| 系统总体设计 | 系统定位、整体架构及主干协作；全部设计主题各自的目标、职责与契约、关键机制、相互关系和约束；模块职责与依赖表；详设映射留在工作计划 |
| 模块主设计 | 职责与边界（含不负责的内容）；带真实签名或输入输出的公开接口；主处理路径；异常与边界行为；本篇理解所需的依赖契约 |
| 核心流程 | 触发入口；参与方；正常路径；分支与失败处理 |

简单模块可以简短，但每个适用要点至少用一句话说明；无法确认的要点说明一次缺失原因，不生成空章。

**中文排版与术语。** 中文句子使用全角标点，引号统一用“”；英文、代码和数字内部保留半角。中文与英文、数字、行内代码之间加半角空格，紧邻全角标点时不加。术语首次出现写作“中文名（`Identifier`）”，此后全篇只用同一名称；没有自然中文名称的标识符直接使用标识符，不自造译名。同一列表的条目语法形式一致：完整句以句号结尾，短语不加句末标点。标题不加句末标点或冒号，避免“其它”“相关内容”“说明”等泛化标题。表格中“不适用”写“—”，信息缺失写“未声明”，不留空单元格；单位写在表头。

**新旧文档的收敛方式。** H1 与文件名主题不一致、正文含生成过程叙述、图表或链接单独成篇、入口页为无说明平铺列表，属于阻断级呈现缺陷，整库检查发现即按正常更新流程修复，不能走无变化短路。其余排版差异只在相应段落因内容更新被修改时一并收敛，不为统一版式改写无关段落。仅修复呈现、不改变含义时保留原最后更新日期。

### 4.5 分类大纲与功能点下钻

**功能需求概括。** 维护者和集成者需要先理解功能解决的问题及适用约束，再阅读实现机制。km 初次编写或更新设计文章时，以原始需求、设计声明和已核实源码为输入，让读者能从正文找到具体功能的规则、结果及边界。内容必须有来源，不能为了补齐结构而增加需求、能力、设计动机或验收结论。

**设计目标。**

- 结构可定位（满足：读者按功能问题找到规则与结果）。
- 机制可解释（满足：读者先理解需求与约束，再理解机制如何回应它们）。
- 事实保真（满足：所有内容有来源，不以完整结构替代缺失证据）。

**方案与机制。** 先按文类选择章节，再识别具体功能点，最后展开各点的需求、机制和结果。这一顺序分别落实结构可定位和机制可解释；来源核对贯穿起草过程，落实事实保真。

C003 根据用户 2026-10-20 提供的大纲确定文类顺序，C005 补充需求与机制的对应规则；C006 保留各类主体章节，仅将参考文献改为按实际互联网资料使用生成。完整运行指令由 [design-outlines](../../../references/design-outlines.md) 单独维护，写作参考只负责路由，不在多处复制模板。

| 文类 | 二级正文大纲（按列出顺序编号） | 内容与图示重点 |
|---|---|---|
| 系统总设计 | 简介、需求、目标、功能设计、架构设计、详细设计、参考文献（按需） | 需求及目标的声明与实现状态；所有功能点及工作计划中的详设映射；系统边界、模块关系和端到端主流程；各设计主题的实质摘要 |
| 功能设计 | 目标、设计、流程、数据与接口、异常与边界、验证要点、参考文献（按需） | 按用户能力及可观察结果分解子功能；逐点解释规则、正常/替代路径、数据变化和结果；复杂功能有对应流程、时序或状态图 |
| 架构设计 | 目标与范围、约束与决策、架构视图、组件与依赖、关键场景、质量与演进、参考文献（按需） | 独立且复杂的架构主题才单列，展开结构决策、边界、逻辑/运行/数据视图和关键场景；总设计保留全局摘要，不重复完整正文 |
| 模块或机制详设 | 目标与职责、对外契约、内部结构、详细设计、流程与状态、异常与恢复、参考文献（按需） | 按实际内部机制下钻算法、缓存、生命周期和并发等；结构、决策或状态图依实际问题选择 |
| 流程或状态专题 | 目标与范围、参与者与契约、流程设计、状态与数据变化、异常与恢复、场景推演、参考文献（按需） | 从实际入口到终止展开，正常与重要替代结果都解释；多方交接画时序，分支画流程，业务状态画状态图 |
| 数据设计 | 目标与范围、模型设计、字段与约束、数据生命周期、一致性与兼容、场景推演、参考文献（按需） | 真实字段、实体关系、写入/更新/清除、持久化和版本兼容；按实体关系与数据转换触发相应图 |
| 接口设计 | 目标与范围、通用约定、接口设计、调用流程、错误与边界、调用示例、参考文献（按需） | 逐接口展开真实入参、出参、错误、权限及副作用；有多步交互才要求流程或时序图 |
| 配置设计 | 目标与范围、配置模型、配置项设计、加载与生效流程、异常与安全边界、配置示例、参考文献（按需） | 来源、默认值、合法值、优先级、保存与生效先后、失败后的真实状态；条件选择和激活流程按需分别配图 |
| 部署设计 | 目标与范围、环境与约束、部署拓扑、组件与配置、部署与变更流程、故障与恢复、参考文献（按需） | 仅在原始资料确有部署设计时生成；区分声明拓扑与已观察实例，不臆造端口、冗余、容灾或运行结果 |

上表适用于设计文章，不强制每个工程生成九类文件。模块主设计可以承担同一功能或技术主题的独立详设；各篇保留独立理解所需的解释，必要复述从同一原始来源核对。技术专题按主要问题选架构、模块、流程、数据、接口或配置大纲，不能以“专题”为由绕过大纲。操作指南、快速入门、查询参考、排障、导航和术语表保持各自阅读目的，不套设计章节。

**总设计的主体与文献。** “简介”说明定位、对象与范围；“需求”列原始声明、参与角色和约束，并区分已实现能力；“目标”列有来源的设计目标与边界；“功能设计”按业务能力逐项说明子功能、入口、规则和结果；“架构设计”解释边界、模块职责与依赖、全局数据和主干协作；“详细设计”逐主题解释关键机制、状态、异常、关系和约束，独立详设对应关系保存在工作计划；“参考文献”仅在本篇实际使用互联网资料时列出。总设计的功能点索引与工作计划中的设计主题对应关系分别维护，两者不能互相代替。

**功能点粒度。** 从用户操作、CLI/API、定时触发及领域声明识别“业务能力 → 具体功能点 → 重要子场景”，不能只列模块、页面或类名。例如来源处理可能包含发现、筛选、复用、追加、重建、移除、失败保留和取消，是否分为独立功能点由真实行为及结果决定；示例不是所有工程必须具备的能力。每个功能点在详设中有可定位正文，写明目标、触发与前提、输入、规则与处理步骤、输出及状态变化、异常与边界、案例、来源和必要图。复杂规则拆为三级主题，简单字段或工具函数留在所属功能内，不一函数一文档。

**覆盖与配图。** 工作计划保留功能点的来源、总设计位置、主要详设与回答章节、适用流程/案例以及配图评估。逐个重要子机制判断图示需求，不能以“本篇已有一张图”结束检查；正常路径、关键判断、异常保留、配置生效、状态转换等若回答不同问题，可分别绘制。允许一张清晰的图覆盖多个功能点，但要能定位对应的条件和结果。图不是按篇数配额，完整语义和文章显示宽度共同决定拆图。

**版式。** 每篇设计有一个 H1、导语、普通链接目录和连续编号正文；功能清单只负责索引，详细规则保留在正文。避免超宽表与长段塞表；复杂流程分图，图紧邻解释段落并附范围、图注和关键分支说明。

**证据与引用。** 必要信息缺失时，必需主体章保留简短且具体的缺失说明；可选细节省略，不铺空标题。“需求”和“目标”缺少原始声明时明确未声明，已实现行为另标为能力事实，不从代码反推历史需求或性能目标。来源与逐项结论的对应记录在 `.cards/`；正文解释必要内容，实际使用的互联网资料按 4.1 生成参考文献。不设置“相关文档”小节，也不为未使用资料保留末章占位。

**检查与修复。** 除原有深度、主题、配图检查，独立检查文类大纲及版式一致性、功能点覆盖。大纲齐全但功能点只有一行摘要仍失败；正文详细但漏真实功能同样失败。当前旧库在无变化复用前重新核对，历史通过不代表满足本规则；同次调用内返回规划或起草做有界修复。C003 保持待人工核验，不因写入本规范代签验收。

#### 需求、目标与机制的对应

本规则使读者在进入实现细节前理解规则目的，并能判断机制回应了哪项需求。对完整设计主题或功能点，按下列顺序展开；字段条目、简单契约和下级规则可以引用上层说明，不重复四套标题，也不限定句数或目标条数。

| 信息层次 | 应说明的内容 | 来源与使用边界 |
|---|---|---|
| 功能需求概括 | 为谁解决什么问题；触发场景、输入来源、可观察结果与硬性约束 | 需求来自原始声明；只有实现证据时标为当前能力，不补造需求 |
| 设计目标 | 从已声明需求与约束推出的设计取向，并指出对应关系 | 无依据的取向不补写；源码不能证明历史设计动机 |
| 方案与机制 | 先说明规则目的与输入契约，再解释动作、依赖、分支和结果；指出其回应的目标 | 机制效果须有依据；不把对应关系写成作者当时选型的理由或效果保证 |
| 边界与非目标 | 已声明的非目标、平台范围、失败后果、空态、回写及适用的事务边界 | 限制靠近相关机制；不能把未核实范围写成能力不存在 |

输入缺失、格式错误或解析失败按项目实际语义说明。分别写清触发条件、对外输出或错误、保留或修改的状态、诊断信息与恢复方式；“空态”“服务错误”是结果语义，“诊断保留”是信息处理行为，可以同时成立，不强制归为互斥三类。没有对应实现时不补写重试、回滚或事务保证。

同维度的输入、字段或条件优先用短表比较，分支和依赖用有序流程或按工程制图规范完成的图解释。服务商四列表只是特定问题的可选形式；正式交付不保留 Mermaid 占位。章节移动在起草阶段处理，同时保持内部来源记录与所支持结论的对应关系。

依据：2026-10-22 用户提供的设计章节编辑提示词及对分析结果的确认；既有文类、事实边界与[单篇编写流程](05-单篇文档编写流程.md#44-表达修订与问题返回)。

#### 详细设计的内容深度

C003 根据用户对详设缺图、内容偏浅的反馈补充本节。总设计解释完整系统，详设展开各自的内部机制；总设计摘要、接口名称清单、类职责表或来源链接不能代替详设。按本主题适用事实展开：入口与前置条件、输入输出和字段约束、按顺序的处理步骤、影响结果的全部关键判断、状态归属和数据变更、失败/取消/恢复、边界及可追溯的处理示例。并发、缓存、持久化、计费等机制存在时解释其有效条件与例外，不为不存在的机制造章节或历史动机。

每篇设计在工作计划中保留读者问题及来源，完成后定位到实际回答章节，并记录配图评估。复杂算法或流程至少按一个正常案例及一个会改变路径的边界/失败案例静态推演，解释中间值、分支和最终状态；标明为按源码推演，不冒充运行实测。短小且完整的单一契约可用精确字段或条件说明，不强凑案例。缺少必要原始依据仍列待续。

验收逐篇检查读者能否依据正文解释执行先后、选择分支、数据/状态变化及失败后果。只有图、只有列表、堆积来源、增加字数、复制代码或重复总体背景均不视为深度达标。图稿必要性另按工程制图设计逐篇判断。内容缺口在同次调用内返回来源阅读和起草修复，不新增用户子命令或审批。

**边界与非目标。** 本节约束设计内容的解释顺序，不替换既有文类大纲，也不要求每个小节重复需求或新增图稿。仅获准修改句子时，结构问题只记录并返回起草，不直接重排标题、段落或表格；缺少需求、目标或结果依据时保留缺口。诊断清单和调整说明进入工作记录，用户要求编辑报告时单独交付，不写入正式生产章节。

### 4.6 来源、限制与元数据

正文直接解释行为、关系与约束，本地原始依据与具体结论的对应保存在 `.cards/` 工作记录中。内部追溯仍须能说明“哪处资料支持哪组结论”，不能用来源路径集合代替逐项核对；读者正文不承载本地资料链接清单。

| 信息 | 呈现方式 |
|---|---|
| 影响读者判断的限制或冲突 | 放在相关结论附近，说明适用条件和实际影响 |
| 一组结论的直接来源 | 本地依据在 `.cards/` 记录路径、符号或锚点及支持关系；实际使用的互联网资料按篇引用 |
| 完整来源关联、读取范围与核对批次 | 按卡片和增量设计记录在 `.cards/`，不转成正文的跨文档来源索引 |
| 未读取或无法确认的范围 | 在受影响结论处说明原因和影响；不以跳转代替说明，不包装为完整覆盖 |

README 导航与 SVG 嵌图的本地路径相对于当前文件解析；来源元数据的 `sources.path` 相对于目标工程根目录解析，二者不混用。内部来源记录可使用符号或文档锚点辅助定位，行号只作为当前定位信息。生成文档和卡片不成为下一轮独立项目事实来源。

静态源码支持当前机制的解释；原文档声明保留其设计或说明属性；推断明确表达不确定性。存在冲突时不静默选取看起来更完整的说法，也不将“未发现”直接写成“功能不存在”。实现用途与通用术语定义可以使用不同来源，遵循卡片的分字段依据规则。

更新时间与核对时间分别维护。源码变动导致解释、契约、限制或引用需要修改时，更新相应正文及其最后更新日期；重新核对后正文不变时，保留原日期，仅更新实际核对记录。引用批次、哈希或版本信息以工具实际取得为准，不能为满足字段制造值。

### 4.7 验证与实现情况

写作检查围绕以下问题进行：阅读目的清楚；页面范围适当；标题层级和链接正确；文类大纲经过裁剪；表格、步骤和代码上下文充分；术语前后一致；关键结论可追溯；未知范围与真实限制可辨；更新时间反映内容变化。

C001 的呈现检查继续保留：H1 与文件名主题一致；页面符合统一骨架，提示与更新日期使用统一写法；正文无生成过程叙述，证据状态不逐段重复；各文类达到最低实质内容，无图、表或链接单独成篇；入口页按阅读目的分组并逐项说明；中文排版与术语首现符合 4.4。原节末依据与相关文档的呈现规则由 C006 的单篇自包含规则替代。

C006 增加 `article_self_containment` 与 `bibliography_usage` 两项必需检查：对每篇普通文章单独阅读，核对必要解释、所有形式的文档转介和共享契约；按本篇查阅与实际使用记录核对互联网引用、文献章与目录项。README 导航、篇内锚点和 SVG 嵌图不能因允许链接被误判。新批次的实际结果及边界见[单篇自包含与参考文献验收](../../../tests/self-contained-articles.md)，历史验收不追改。

C004 增加句子语义检查：逐动作核对主体、动词和对象，保留条件的作用范围、否定、先后及确定性；结果只能来自已核实内容。修订前后分别核对段落结构与保护字面量，并用来源审阅句子含义；结构校验不能证明语义等价。检查只覆盖允许修改的段落，不为统一句式重写稳定正文。

C005 增加需求与机制对应检查：完整功能点先交代需求起点和约束，设计目标可追溯，机制说明其回应关系；细则有目的和输入契约，异常按实际结果、状态与诊断行为说明。发现结构或来源缺口时返回规划或起草，不以句子润色补造事实。对本文件 4.5 的逐段诊断、修改说明和回查见[需求先行写作检查](../../../tests/requirement-led-writing.md)，不将单份样本检查表述为整库质量保证。

T02 增加分层检查：模块识别有来源；每个业务模块均独立主设计；总体摘要及入口无遗漏；必要专题未完成不能以主文件存在判定模块完成；复杂跨模块流程的主要解释与各模块引用一致。

结构与语法检查不能代替来源语义审阅。检查采用宿主已有工具或模型审阅时，分别记录真实检查方式、读取范围和未核对项，不宣称存在 km 专用检查脚本或确定性执行能力。

本版本由[写作参考](../../../references/writing.md)承载本规范并接入 workflow。T01 和验收说明记录实际样例及检查范围；治理检查不能证明内容完全正确或人工验收完成。
