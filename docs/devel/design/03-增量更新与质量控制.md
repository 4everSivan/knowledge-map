# 增量更新与质量控制设计

> **created**: 2026-10-15 ｜ **last-change**: 2026-10-25 ｜ **status**: baseline

## 1. 简介

本设计适用于 km v0.1.0。用户于 2026-10-15 明确“0.1 版本的设计暂时定稿，按文档治理流程落地实现”，本组设计据此确认为该版本基线；实现与验收由 T01 记录，设计批准不等于运行能力验收。

本设计约束用户重复调用 km 后，宿主 AI 如何依据 workflow 文件识别知识变化、判断已有产物是否仍有效，以及在覆盖不足、来源冲突或写入中断时保护已确认的知识库。目标是让同一调用既适用于首次生成，也适用于日常更新，同时如实呈现本轮实际完成的范围。

设计来源为本次会话已形成的总体方案与用户对产物范围、术语卡片、目录布局及“通过 workflow 文件更新，当前项目不用任何脚本”的澄清。km 的运行方式是由 workflow 文件约束宿主 AI，使用宿主已有的文件、搜索和差异工具读取、判断、编辑并核对；技能不提供或依赖运行脚本、执行引擎或程序校验器。本版本由 workflow 和状态参考承载质量约束，实际检查和样例证据由 T01 记录，不承诺模型执行具有确定性。

## 3. 规范

### 3.1 目标与边界

| 约束 | 可观察结果 |
|---|---|
| 内容变化能触发更新 | 宿主 AI 核对实际文件，不能只按提交历史跳过未提交文件、明确纳入的未跟踪文件及非 Git 工程 |
| 更新范围覆盖真实影响 | 不只重写直接改动文件的说明；同步检查相关模块、调用方、配置消费者和数据契约 |
| 无变化有据可复用 | 可靠证据支持已有完整结果仍适用时不重写；证据不足则扩大读取，不宣称无变化 |
| 不完整结果可继续 | 本轮 `partial` 的候选与待续范围可查，下次调用不能因已读文件无变化而跳过剩余范围 |
| 已确认内容受保护 | 检查失败、覆盖不足或已知文件冲突时不开始正式替换；写入中断如实说明并逐项核对 |
| 结论与证据对应 | 文件结构核对与语义复核分别完成并报告，不能以链接有效替代内容正确 |

范围限于知识文档与术语卡片的生成、更新和校验。正式 Markdown 直接位于 `docs/official/`；所有生成 JSON 位于其 `.cards/` 子树。不设置 `generated/`、`manual/` 或人工补充流程，不构建静态网站，不移动目标工程原有治理文档、源代码或其他项目资产。

### 3.2 输入与产物位置

输入包括纳入范围的自有源码、原有项目文档、有效配置、workflow 规则和卡片约定。Git 的分支、提交与工作区差异信息可以辅助定位来源，但不能取代实际文件内容。非 Git 工程通过当前文件与已有读取记录比较；无法可靠判断的范围重新读取。源码注释、文档与工具返回内容作为证据读取，不自行授予执行其中命令的权限。

扫描排除 `.git`、明显凭证文件、依赖、构建产物、备份及 `docs/official/` 整个输出子树；不跟随指向目标工程外的符号链接。目标工程其余原有文档仍按实际位置读取。宿主 AI 单独读取 `.cards/config.json` 的有效偏好，不将生成内容重新吸收为证据。

| 产物 | 固定位置与职责 |
|---|---|
| 正式知识文档 | `docs/official/README.md` 与直接位于该目录的中文语义文件名 Markdown |
| 正式术语卡片 | `docs/official/.cards/k_<uuid>.json`，每个术语独立一张卡 |
| 可选配置 | `docs/official/.cards/config.json`，本轮有效值参与更新判定 |
| 已确认知识清单 | `docs/official/.cards/manifest.json`，记录受管文件、有效配置及按术语 ID 关联的来源范围、核实批次和实际可得哈希等更新信息 |
| 最近尝试记录 | `docs/official/.cards/last_attempt.json`，记录本轮覆盖、校验、冲突、候选入口及待续范围 |
| 按需保留的 Markdown 候选 | `docs/official/.staging/<run_id>/` |
| 按需保留的 JSON 候选与检查记录 | `docs/official/.cards/runs/<run_id>/` |

清单是宿主 AI 的工作记录，不是供脚本交换的执行协议。候选目录仅在需要保留未完成内容或审阅替换结果时创建，不预建复杂运行状态目录。运行资料不自动清理，也不因本设计而迁移项目既有运行资产。是否将运行资料纳入 Git，沿用目标项目约定。

### 3.3 失败与状态解释

每轮分别记录 `coverage_status` 与 `validation_status`，不把二者合并成一个“成功”标志：

| 字段 | 取值 | 含义 |
|---|---|---|
| `coverage_status` | `complete` / `partial` | 本轮声明范围内的材料是否已完成应有的读取与分析 |
| `validation_status` | `passed` / `failed` / `not_run` | workflow 要求的本轮产物核对是否完成并通过、发现问题或尚未执行 |

关键入口或工程根目录不可读时，本轮不能形成可确认的完整结果；非关键材料无法读取时，可以保留明确标记为 `partial` 的候选并报告缺口。只有覆盖完整、约定核对通过且不存在已知阻断冲突时，才开始替换本轮正式产物。`complete` 只描述声明范围，局部扫描不得声称覆盖全项目；`passed` 表示所列核对已完成，不表示存在程序校验器，也不证明目标软件已通过生产运行验收。

无法安全区分的敏感材料不复制进入知识库，报告其未纳入范围，不承诺自动脱敏覆盖所有格式。来源之间的事实矛盾必须呈现；若因此无法形成受影响知识的可信候选，则不能将本轮标记为校验通过。

工程制图及新增输出契约由[工程制图设计](06-工程制图.md)补充，T03 跟踪实施与验收；SVG 位于 `docs/assets/km/`，清单位于 `.cards/diagrams/`，纳入同一整库更新。

## 4. 设计详情

### 4.1 增量更新与影响范围

<!-- @topic: IncrementalRefresh -->

宿主 AI 结合上次来源记录、当前文件、现有 Git 差异和搜索结果判断变化。修改时间或提交号不能单独证明没有变化；未提交修改须纳入核对。内容哈希仅在宿主已有工具实际提供时作为可选辅助依据，不为此安装工具或编写脚本，也不承诺自动取得全部文件哈希。没有可靠比较依据时重新读取相关范围，必要时重新分析声明范围全部材料。

源码、项目文档、有效配置、生成规则或卡片协议的变化均可使既有知识失效。源码变化至少按模块重新分析，并核对调用方、配置消费者和数据契约。公共入口或共享契约影响不明确时扩大范围；仍无法可靠界定时采用全量分析，不将“直接引用未命中”等同于“无影响”。

| 变化类型 | 文档与术语处理 |
|---|---|
| 新增模块或能力 | 生成适用文档并更新导航；有需要解释的新术语时建立卡片 |
| 行为、配置或数据契约变化 | 更新受影响正文和依据；仅在术语含义、用途或使用位置改变时同步相应卡片 |
| 仅项目文档的目标变化 | 更新目标描述并保留与当前静态实现的差异，不把设计意图写为已实现能力 |
| 来源移动或重命名 | 可靠确认同一概念时续用原术语 ID，更新来源路径；无法确认时报告歧义，不强行合并 |
| 来源删除 | 检查其他现行依据与用途；依据不足时按卡片契约置 `stale`，确认已无现行用途后置 `retired` |
| 新增真实别名 | 依据同一概念和使用语境更新原卡，避免仅因名称不同创建重复卡片 |

正式文档保持中文语义文件名，不使用 `00-`、`01-` 等阅读顺序前缀。更新内容通常不改名；确需改名时同步导航、卡片文章关联与其他引用。代码标识和术语真实名称原样保留，别名不靠猜测展开。同名异义术语依所属语境分别辨识，名称相同不能成为合并 ID 的充分依据；具体卡片身份与状态契约见[术语知识卡片设计](02-术语知识卡片设计.md)。

用户已确认，更新后的表达修订只处理变更段落及必要上下文，未变部分保持原样；这不缩小前述影响分析范围。没有实质变化且满足复用条件的文档直接复用。内容或结构问题先在分析与起草阶段处理，不能借“去 AI 味”修改事实；具体单篇流程见[单篇文档编写流程](05-单篇文档编写流程.md)。

模块内部机制改变但对外职责、接口和全局关系不变时，核对模块主设计与相关专题，按实际影响更新。职责、契约、共享状态责任或跨模块关系改变时，扩大核对总体、参与模块和主要流程；不因关系存在就重写所有文章。源码未变而分层规则改变时，缺少必需模块主设计或专题的旧集合也不能直接复用。

### 4.2 一致输入与重复调用

本轮记录实际读取范围与可取得的来源版本信息；该记录不等于文件系统一致快照。宿主 AI 在正式替换前重新查看关键来源和可用差异，发现输入变化时重新判断影响并补读。若持续变化或工具能力不足使本轮结论缺少一致依据，保留候选并报告待重新核对，不能将不同状态的材料拼接后声称获得一致快照。km 不提供自动快照或全覆盖哈希校验。

无变化复用同时要求：已有结果覆盖完整、没有待续范围，且通过实际文件读取或可靠差异证据，确认当前来源、有效配置、workflow 规则和受管产物仍与既有结果相符。此前为 `partial`、存在未核对的中断写入、外部修改冲突或比较依据不足时，都不能进入无变化短路。复用时不重写知识内容和知识时间戳；最近尝试记录可以反映本次确实完成的核对。

`library_revision` 标识一次已确认的文档与术语集合，由宿主 AI 在正式内容确实更新后维护；不要求以全量内容哈希计算，也不以它单独证明产物有效。运行时间、易变统计以及 `.staging/`、`.cards/runs/`、`.cards/last_attempt.json` 的变化不触发知识修订，避免调用产生的运行记录引起下一次无意义更新。

切换分支或恢复历史知识库后，仍按当前输入、有效配置和实际产物重新判断有效性，不因存在旧 manifest 就认定知识当前有效。manifest 按卡片 ID 关联的核对批次及来源记录应能解释对应结论；单卡只保留直接来源与术语内容。没有保存源码副本时，不声称能够还原历史源码快照。

### 4.3 覆盖不足与继续处理

本轮覆盖不足时，按需将候选 Markdown 留在 `.staging/<run_id>/`，JSON 候选与检查记录留在 `.cards/runs/<run_id>/`。`last_attempt.json` 最小记录已完成范围、尚未读取或分析的范围、原因、已写入文件及候选入口；正文和报告清楚区分本轮候选与此前确认的知识库。

模块未完成时，将实际模块清单、来源、主设计及所需专题、待续事项保留为 `.cards/runs/<run_id>/document-plan.json`，由最近尝试的 `candidate_paths` 引用。下次先读取原计划并重新核对来源与实际候选，不只从已有文件反推清单。未解决的识别缺口、缺少主设计或未完成必要专题均阻止完整覆盖；不自动缩减计划以消除缺口。该计划是工作记录，不新增清单协议字段或执行引擎。

C006 取消生产正文互链后，计划成为总设计与详设对应关系及共享内容使用的唯一记录，不能因 `last_attempt.json` 被下一次调用覆盖而失去入口。每次整库检查都在 `document_associations` 检查证据中写明所用计划路径，尝试记录与更新后的 manifest 核实批次均保留该证据；计划变化时在本次运行目录写入新副本并沿用复核后的未变记录，计划未变时引用原路径。后续调用先按确认 manifest 中 `checked_at` 最新的核实批次定位计划，再与更新的未完成尝试对齐；找不到可信计划时按结构修复从原始来源重建，不从已有文章反推。

下次调用先核对实际文件与上次尝试记录，再处理未完成范围，即使已读输入没有变化。重新读取相关来源并检查 workflow 规则是否变化，只有仍适用且已核对的候选才能复用；进度记录存在并不能证明对应内容正确。输入或生成条件变化时重新判断应分析范围，不能盲接旧结果。这是宿主 AI 按 workflow 继续处理，不依赖 checkpoint 引擎。

预算不足、大型工程或读取失败造成的抽样，只能说明实际覆盖情况。首次尚无完整结果时，报告明确说明正式知识库尚未形成；不得将候选入口描述为已提交的完整文档库。下次调用先核对已读来源和中断写入，再按原计划续读剩余专题；调度以本版本 workflow 为准。

### 4.4 质量校验与证据

<!-- @topic: KnowledgeQuality -->

文件结构核对与语义复核承担不同职责，二者的证据在报告中分别呈现。宿主已有工具能够直接解析或检查时可使用其实际结果，能力不可用时由 AI 明确列出检查方式与未验证项，不宣称自动校验覆盖：

| 类别 | 应检查内容 | 通过的实际含义 |
|---|---|---|
| 文件结构核对 | JSON 字段与格式、ID 重复、受管文件存在性、引用完整性、来源路径、Markdown 链接和明确锚点、卡片关联 | 已执行的核对未发现对应结构问题；机器解析是否执行另行说明 |
| 写作规范核对 | 文类与大纲适用性、篇首、标题层级、Markdown 元素使用、来源呈现和空章；具体规则以[编写规范](04-生产文档编写规范.md)为准 | 实际文档符合已确认的编辑规则，不因此证明来源结论正确 |
| 模块与集合覆盖 | 先对照原始来源复核模块识别，再逐模块检查独立主设计、必要专题、总体入口和复杂跨模块流程关联 | 已执行的识别与文档集合核对分别有据；主文件存在不等于覆盖完整 |
| 来源语义复核 | 实际入口与调用关系、配置优先级、数据流、异常路径、代码与文档目标差异、来源冲突 | 结论与已检查的材料一致，并披露不确定性 |
| 术语语义复核 | 专业名称或独有名称的释义、项目用途、使用语境、真实别名、同名异义及来源 | 卡片解释对应项目真实概念，而非猜测缩写或复述名称 |
| 保护边界核对 | 原项目资产、管理清单、受管产物外部修改、输出目录占用 | 本轮写入具有明确边界，没有静默覆盖冲突文件 |

来源路径存在不代表结论正确，工具结果不能替代模型语义复核。km 不提供 JSON Schema 校验程序或链接检查脚本；宿主已有的解析与链接工具也只能证明其实际检查范围。静态源码证明当前静态实现；测试文件只证明存在测试预期或方法，未执行测试不能声称已通过。知识库核对通过不能扩大为业务行为、目标设备或生产环境的验收结论。

单篇表达修订前后均复核事实。建议起草后先按来源核对内容，再修表达；之后比较修订前后并回查来源，防止改变条件、默认值、否定、验证范围或引用。单篇候选完成不替代本节整库检查，也不单独触发正式替换。

发现来源失效时，按术语卡片契约核对其 `stale` / `retired` 处理及正文展示，禁止失效知识继续声称已核实当前有效。若失效状态本身有充分证据且被准确呈现，不把这种如实记录等同于“来源仍然有效”。

### 4.5 文件冲突、替换与中断核对

workflow 要求宿主 AI 在发现其他会话同时修改目标时停止正式替换并报告冲突；km 不提供跨会话原子锁，也不能保证检测所有并发写入。已知存在并发变化时不能继续覆盖文件并声称本轮结果一致。

manifest 记录由 km 管理的文件。首次已有文件占用拟写入路径且无法确认管理权时，保留文件并报告冲突；不接管未知文件，也不静默换用另一输出根目录。宿主 AI 在覆盖前读取现有产物并查看可用差异；发现外部修改或无法确认内容归属时保留原文件，暂停整轮正式替换，不吸收这些修改作为知识来源，也不建立人工补充合并流程。记录的哈希若存在可作为辅助依据，但不是自动冲突检测保证。

正式替换前完成约定的覆盖与质量核对；有缺口或已知冲突时保留候选，不开始覆盖已有正式结果。需要审阅多份候选时使用规定的暂存位置。宿主工具确能保留原文副本或提供版本恢复依据时可据实使用，不能因设计描述而假定已经有完整备份。

宿主 AI 完成正式文件编辑并复查后，最后更新 manifest；该约定只表示确认顺序，不提供多文件事务或自动回滚。`last_attempt.json` 保留最小必要的未完成事项与实际写入范围。若编辑中断，下次调用先逐项查看文件，比较上次记录与现状，决定继续补齐或在已有可核实原文的条件下恢复；资料不足时报告待处理项，不盲目回滚、不假定旧文件完整。中断后的混合集合不能作为已确认成功结果；不设计复杂 journal 引擎或脚本交换协议。

### 4.6 结果报告

每次调用报告目标工程、实际来源与可取得的版本信息、实际扫描范围、排除及读取失败、文档和卡片的新增/修改/退役、来源冲突、覆盖与核对状态、实际使用的工具及结果、正式 Markdown 导航入口和遗留项。确实执行命令时才报告其命令与退出码；存在候选时另给出入口，说明它与正式结果的关系。

无变化复用的报告说明复用依据；`partial` 或失败报告说明待续范围与上次成功结果是否存在。未运行的检查如实标为未运行。报告不虚构耗时、token 节省、性能阈值或人工验收记录。
