# km 项目知识库技能

km 根据项目代码和原有文档，生成可追溯的中文 Markdown 文档库、JSON 术语卡与有据工程图。源码或文档变化后，再次调用同一技能，更新受影响内容。

当前版本 v0.1.0（2026-10-26 发布，本批次卡片已归档至 [docs/archive/v0.1.0/](docs/archive/README.md)），变更明细见 [CHANGELOG](CHANGELOG.md)，任务状态见 [任务总账](docs/devel/task/index.json)。

## 使用

将本目录作为名为 `km` 的技能载入宿主。在支持显式技能调用的宿主中，在目标工程调用：

```text
$km
```

一次调用内完成取证、规划、总设计与详设、图稿、检查、有界修复和整库交付；日常生成步骤连续推进，必要来源、权限或预览能力缺失时如实保留待续。

首次调用不需要配置。也可以在请求中指定目标工程和范围。`/km` 是否可用取决于宿主的命令适配；本项目没有独立注册 slash command，当前未实测该入口。

默认输出：

```text
docs/official/
  README.md
  项目名设计文档.md     # 必需：逐主题说明全部设计并链接详设
  任务调度设计.md       # 示例：每个识别出的业务模块都有独立主设计
  任务调度-状态流转.md  # 示例：模块复杂细节按需拆专题
  任务分派流程.md       # 示例：复杂跨模块流程独立说明
  配置参考.md
  术语表.md
  .cards/
    k_<uuid>.json
    manifest.json
    last_attempt.json
    diagrams/d_<uuid>.json
```

图稿放在 `docs/assets/km/*.svg`，文章通过相对路径引用；每图语义清单在 `.cards/diagrams/`。

文档使用中文语义名称，不加排序数字。卡片解释专业术语、缩写和项目独有名称，分别保留 `definition` 与 `project_usage`，可以关联多篇文章。核实批次、时间和实际取得的哈希集中在 manifest。

## 工作方式

宿主 AI 先理解全局架构，再按专题阅读原始资料并编写候选，最后统一检查和交付。单篇首次编写经过分析、起草与来源核对、表达修订、事实回查；更新先比对受影响结论，只修变更段落及必要上下文。无实质变化且证据可靠时保留原文和内容日期。

生产文档按项目正式技术文档的标准呈现：统一页面骨架、提示与最后更新日期，各文类达到最低实质内容，图、表或链接清单不单独成篇；正文使用中性陈述，不叙述生成过程，依据类型在入口页集中说明一次。普通文章独立完整，必要定义、契约、流程和边界直接融入本篇，不链接其它文章或原项目资料；README 导航、篇内目录与 SVG 嵌图保留，完整本地来源关联记录在 `.cards/`。H1 与文件名不一致、过程叙述等阻断级呈现缺陷在整库检查时修复，其余版式差异随内容更新逐段收敛。

总设计为必需产物，逐主题解释目标、职责与契约、关键机制、关系和约束，每个主题另有对应的独立详细设计；两者的对应关系记录在工作计划中，正文不互链。主题从原设计、职责与实际调用共同识别，同一平台中的独立设计仍分别成文；总设计不能只剩架构概览或模块目录。所有识别出的业务模块也保留独立主设计，复杂机制按需拆专题，复杂跨模块流程维护一处完整说明。工作计划记录“设计主题—总设计章节—详细文档—来源”的对应关系；交付分别检查主题覆盖、中文命名和当前关联，缺失项不能以 `complete/passed` 带过。

设计文档采用九类大纲：总设计、功能设计、架构设计、模块或机制详设、流程或状态、数据、接口、配置、部署。总设计使用“简介、需求、目标、功能设计、架构设计、详细设计”主体章节；各类文章仅在本篇实际使用已查阅的互联网资料时增加“参考文献”，否则连同目录项省略。其它类别按各自目的展开，详细中文约定见[分类大纲与功能点下钻](docs/devel/design/04-生产文档编写规范.md#45-分类大纲与功能点下钻)，执行参考见[设计大纲](references/design-outlines.md)。文件名不加序号，设计正文统一编号并提供篇内目录。

先从实际入口识别业务能力、具体功能点和重要子场景，再映射到总设计及独立详设的正文、案例和图稿。功能清单只做索引，每个复杂功能仍须解释触发、输入、规则、步骤、结果、异常与边界。配图逐功能和重要机制判断，不能以一篇已有一图代替完整评估。

详设按各自的内部机制展开：实际契约、处理顺序、关键判断、状态和数据变化、失败与恢复；复杂流程给出正常及边界案例的源码推演。工作计划逐篇记录读者问题、回答章节和配图评估，交付单独检查内容深度及逐篇图稿覆盖，不能凭篇幅、标题或文件数量认定完成。

工程图先从原始来源生成并核对语义清单，再绘图，最后核对正文与实际渲染。按模块协作、复杂交互、内部算法分支、数据转换与业务状态逐篇判断必需图，并由 AI 按需补充；同图共享，不同视角另画，实现与目标分图。正式图稿须实际检查 Markdown 内嵌和独立 SVG。缺少必需的预览能力时如实待续；选配图可在修复全部引用、确保正文完整并通过整库检查后暂缓。

选图按架构、控制流程、调用时序、生命周期状态、数据血缘、实体关系、部署位置和依赖方向分别评估，触发条件见[工程制图设计](docs/devel/design/06-工程制图.md#八类图的触发条件)。工作计划保留八类判断和具体理由，`figure_view_coverage` 单独核对必要视角；文章已有流程图仍须判断其它视角是否缺失。类型数量与比例只作描述，实际来源和图中语义决定是否充分。

输出不作为下一轮的独立项目事实来源。覆盖不足时保留候选和待续记录；发现输出文件占用或外部修改时停止正式替换并报告。下次调用先核对未完成记录与实际文件，再继续处理。

默认使用当前项目和中文正文。需要限定范围时，可在 `docs/official/.cards/config.json` 中设置受支持的偏好，字段见[状态参考](references/library-state.md)。不需要为首次使用创建该文件。

## 技能组成

分发所需的执行资源只有：

| 资源 | 职责 |
|---|---|
| [SKILL.md](SKILL.md) | 技能名、触发范围、贯穿各阶段的证据与诚实原则，以及各规则的归属参考 |
| [workflow.yaml](workflow.yaml) | 四个英文阶段（范围、规划、编写、检查与交付）的动作、完成条件、失败去向及运行报告 |
| [assets/diagrams/base.svg](assets/diagrams/base.svg) | 静态 SVG 基础模板 |
| [references/](references/) | 按需加载的写作、单篇流程、表达修订、术语及状态契约；每条规则只在一个参考中完整表述 |

制图采用本地英文参考与八类图型规则；出处和 MIT 声明见[上游说明](references/diagrams/upstream-notice.md)。manifest/尝试协议为 `2.0`，图稿语义清单为 `1.0`；当前不提供旧库迁移。

km 不依赖运行脚本、工作流引擎、模型 API Key 或网站框架。现有 `scripts/adflow-verify` 是维护本项目的治理工具，不是 km 的运行依赖。

## 验证与限制

开发检查包括技能基础格式、YAML/JSON 解析、参考路由和治理检查。T01 的 12 个历史样例见[初版验收记录](tests/acceptance.md)，T02 的 7 个模块分层样例见[分层验收记录](tests/module-docs.md)，T03 的八类图、双阅读环境及更新/失败场景见[工程制图记录](tests/diagrams.md)。这些均为同会话演练和文件核对，不能代替独立宿主触发测试或完整模块发现保证。

C003 的[总设计与主题详设验收](tests/design-coverage.md)记录独立子会话显式加载已安装技能的前向生成、四组反例审阅、增量刷新及 Bruce 真实文档整理；保留失败、修复和有界独立复核记录。

新增[详设深度与逐篇配图验收](tests/detail-depth.md)记录复杂样例的连续生成、内部图与案例、独立审阅、三组反例及最终路径修复；旧 Bruce 两篇文档按新标准被判待补齐，不能沿用首轮覆盖结论作为深度通过。

[分类大纲与功能点验收](tests/design-outlines.md)记录五类设计的实际生成、具体功能下钻、七组图稿及实际版式检查，并验证大纲齐全但缺关键规则的候选仍被拒绝；九类大纲按项目事实选择，不强建无来源的文类。

[图型触发与视角验收](tests/figure-views.md)记录同一功能实际生成流程、时序、状态和数据流四个视角，以及旧图保留复用但仍缺必要视角的独立审阅；候选通过与整库待续分别记录，不以图型标签或数量证明覆盖。

当前未验证宿主自动发现 `$km`、`/km` 注册、任意大型工程的完整主题发现或持续并发修改。T03 的实际写入中断仅覆盖前向引用断言失败后的记录与续跑，未覆盖文件系统故障。不会把静态代码阅读写成业务运行或生产验收结论。多文件替换没有事务或自动回滚保证。

研发规则、设计与任务记录由[文档中心](docs/README.md)导航。对表达修订规则的参考来源固定到上游提交，见[英文参考的出处](references/technical-editing.md#provenance)。
